# cf-loom

Organization-agnostic tooling for Service Contracts: HTTP Endpoints and messaging, written in TypeScript with zod. This repository holds the tools, and in `examples/` fictional Services and the Definitions Package they share, used as end-to-end tests; never a real Service's Contract. The design is in the documents below; the packages are under `packages/`.

## Documents

| File | Holds |
| --- | --- |
| `CONTEXT.md` | The glossary: every term, with words to avoid |
| `COMPATIBILITY.md` | How a Contract may change: the Compatibility Check and its rules |
| `ARCHITECTURE.md` | How the pieces fit: packages, runtime, the Wire protocol, what cf-loom leaves to the organization |
| `SNAPSHOT.md` | The Snapshot format the Compatibility Check compares |
| `CODING_STANDARDS.md` | How the code is written and reviewed (C1–C30) |
| `WORKFLOW.md` | How an issue becomes code on `main`: plan, Definition of Ready, implement, review, fix, Definition of Done, merge |
| `README.md` | What cf-loom is, a first Service, and the packages table |
| `packages/<pkg>/README.md` | How to use the package: its API, options, examples |
| `packages/<pkg>/ARCHITECTURE.md` | The package's internal details, repo only (not in the package's `files`) |

- Everything is written in English, code and documents alike.
- No `docs/` folder: a compatibility rule goes in `COMPATIBILITY.md`, an architecture concern in `ARCHITECTURE.md`.
- Each rule lives in one document; the others link to it.
- The documents describe the current design only, never the history of decisions. A changed decision replaces the old text.
- Use the glossary's terms, spelled as their entries, and never an _Avoid_ word as a name for its entry's own thing; `scripts/check-terms.ts` fails on a multi-word term spelled otherwise.

## Repository

- pnpm 12 workspaces under `packages/` and `examples/`, every example `private: true`; shared versions in the catalog of `pnpm-workspace.yaml`. Node 24.16.0 (`.node-version`), with the npm it bundles.
- ESM only; built with `tsc -b` and project references; tested with Vitest projects; formatted and linted with Biome.
- Each package has `tsconfig.build.json` (src to dist, no tests) and `tsconfig.test.json` (type-checks tests); `contract` and `client` build without Node types, since Applications run them in browsers.
- cf-loom packages depend on each other only as peers (plus a devDependency), never as dependencies.
- A package shares code with other cf-loom packages only through an undocumented `./internal` export; no README lists it.
- Relative imports name the `.ts` file (`./serve.ts`); `tsc` rewrites them to `.js`. Only erasable TypeScript syntax: no enums, namespaces or parameter properties.
- `tsconfig.tooling.json` type-checks root files (`*.config.ts`, `scripts/` except `scripts/readme-service/`, which compiles only once written out, and `packages/messaging/test/test-process.ts`, which `scripts/vitest-config.test.ts` imports).
- `lint/` holds Biome GritQL plugins, `scripts/check-tsdoc.ts` checks TSDoc and `scripts/check-expect-errors.ts` checks that each `@ts-expect-error` names the error its line fails with, all for [CODING_STANDARDS.md](CODING_STANDARDS.md).
- `.claude/` holds the agents, the `review-pr` workflow and the settings that [WORKFLOW.md](WORKFLOW.md) names; Biome skips `.claude/workflows/`, whose scripts end in a top-level `return`.
- `scripts/readme-service/` holds, as runnable code, the part of the Service the READMEs describe that no README block shows (the rest of its Definitions Package, its own repositories and Handlers, the rest of `payments-service`, the session file of `web-admin`, the rest of `notes-service`, the small Service of the contract README's first declarations and the server README's HTTP-only example, and the package.json of each of the three Services: the README's own, `notes-service` and `payments-service`) and the tests that run the READMEs' own blocks, in `test/*.readme.test.ts`. When `vitest.config.ts` loads, `writeReadmeService` (`scripts/readme-snippets.ts`) writes it, those tests and the TypeScript blocks of the contract, handlers, messaging, server, client and testing READMEs to a folder of its own under `.readme-service/`, one for each Vitest process, which Git and Biome skip and the process removes when it exits (a restart of Vitest for a change to the configuration loads it again in the same process, which rewrites the folder and registers no second removal; a process ended by a signal after such a restart, or killed with SIGKILL, leaves its folder, since Vitest drops its SIGINT and SIGTERM handlers when it closes for the restart, and deleting `.readme-service/` clears it), so a change goes in `scripts/readme-service/` or a README and two Vitest processes in one checkout never replace each other's files; it then runs `cf-loom generate` and `cf-loom package` over each Service the scope gives a package.json, `notes-service` and `payments-service` first and the README's own at the root last, which writes their Handler maps and Readers files, with the Stubs of the Handlers no block or scope file shows, and their Contract Packages to each Service's `.cf-loom/contract-package/`; it builds each Contract Package with `tsc` and installs it with the Definitions Package, `definitions/`, in the written-out `node_modules`, where every Service, `tsc` and Vitest find them by name; so it needs the CLI built, as `pnpm test` builds it, and what stops a Service, a refusal of cf-loom or a Contract Package that does not build, is reported by the check below at its README line or its file, as `<step>: <package name>: <message>`. cf-loom runs over every Service, and `tsc` type-checks the blocks only when none was stopped, since it checks them against the files cf-loom writes, saying it did not run otherwise; the `readme-service` project's tests then fail with that report instead of the imports they cannot make. A block is completed with an import of each name TypeScript cannot find in it, read per file from its API so that one block's error hides no other file's names, from the modules [Layout](README.md#layout) names, and written as the file its path comment names, one file for each path comment of a block that names several; a path comment's path is a Service path, `src/…` or `<service>/src/…` ending `.ts` with no `.` or `..` segment, and a block whose path comment is not one is a problem and is left out, as is a path two blocks, a block and the scope, or two snippets name. A block with no path comment is written to `snippets/<package>-<heading>.ts` and exports what it declares, so a test arranges its state, with the scope's `resetServiceCode` in `beforeEach`, then `await import()`s the block, and calls `vi.resetModules()` between two imports of one block. Vitest gives the folder to the `tooling` and `readme-service` projects as `inject('readmeService')`. The `readme-service` Vitest project runs that folder's `test/`, finding each scope package by name in the written-out `node_modules`, with `fsModuleCache: false`, since each folder is a new path and its modules would otherwise stay in Vitest's cache for good, and `scripts/readme-snippets.test.ts` type-checks that folder where it is, each error at its README line, so a block that does not compile, or that a README test runs and breaks, fails `pnpm test`. The CLI README's two `ts` blocks are not checked.
- Every package under `packages/` lays out its `src/` as [Package layout](ARCHITECTURE.md#package-layout) says; `scripts/check-layout.ts` checks it.
- Tests sit next to the code (`*.test.ts`) and import as [C23](CODING_STANDARDS.md#tests) says.
- The examples follow [Layout](README.md#layout) in README.md, with their tests in `test/`: `org-definitions` (`@org/definitions`, a Definitions Package), `orders-service` (a Provider) and `billing-service` (its Consumer), both Services listing `@org/definitions` as `workspace:*`. Orders follows Layout; billing places its Handlers in its Group's folder, `src/billing/`, through `src/{group}/{name}.handler.ts`, and its generated files in `src/generated/` with `layout` in its `cf-loom.config.ts`. Each Service has one `tsconfig.json` and runs from source. orders' Contract Package is not committed: `pnpm build` builds the CLI and org-definitions, writes it to orders' `.cf-loom/contract-package/` with `cf-loom package`, then runs `tsc -b`, where orders' `tsconfig.contract-package.json` builds it; billing lists it as `link:../orders-service/.cf-loom/contract-package`, so `pnpm install` passes before it exists. The Definitions Package's `tsconfig.json` type-checks it and its `tsconfig.build.json` builds `src/` to `dist/`, which the Services and the CLI load. The other generated files are committed: every example's `contract.snapshot.json` and the Services' `src/**/*.generated.ts`, which tests check with `cf-loom verify`; orders' `generated.test.ts` checks that the Contract Package billing links is what `cf-loom package --out` writes. After changing a declaration, run org-definitions' `pnpm generate`, which also builds it, then orders' `pnpm generate`, then `pnpm build`, then billing's `pnpm generate`. Biome skips `contract.snapshot.json` and the Services' `src/**/*.generated.ts`, which `verify` compares byte for byte; `.gitignore` keeps `.cf-loom/` out of git and of Biome. `.changeset/config.json` ignores `@org/*`, the examples. `packages/cli/src/examples.test.ts` publishes temporary copies of all three, in that order, to a fake registry it starts on a free port, each installing from its tarballs what the ones before it published, and checks changed copies of the examples against them; it writes nothing in `examples/`. Both Services' `main.ts` run messaging over NATS JetStream and refuse to start without `NATS_URL`; billing's `test/over-nats.test.ts`, the examples' acceptance test over NATS, and `test/over-http.test.ts` start a nats-server of their own with `packages/messaging/test/nats-server.ts`, apply the Broker plans `broker-plan --json` prints, and start the Services' `main.ts` with an environment they write out, never the test's own; so billing's `tsconfig.json` has the repository as its `rootDir` and includes that file and `test-process.ts`, the process code its tests share with messaging's (its `service-process.ts` starts the Services through it).
- The CLI's tests run it with the environment `packages/cli/test/no-registry.ts` gives every test file: an npm that is offline, whose registry is an address nothing listens on and which reads no npmrc of its user's, so no test reaches a real registry or uses a login; a test that needs a registry starts the fake one and gives the CLI its environment.
- Tests that need NATS JetStream start their own `nats-server` from `PATH` with `packages/messaging/test/nats-server.ts`: a random local port read from its ports file, and a temporary store; never a fixed port or another NATS. Every process or temporary directory a test creates through `packages/messaging/test/test-process.ts` (the two servers and the store, billing's Services through its `service-process.ts`, and the Node processes of `scripts/vitest-config.test.ts`) is owned from its creation and killed or removed at the end of its test, which also owns what its `beforeEach` and `afterEach` create, or of its file when a `beforeAll`/`afterAll` created it, in reverse order of creation, through the hooks `test-process.ts` registers in each file that imports it; creating one outside a test or hook throws. A killed process is assumed to have no children of its own, which its SIGKILL would leave running. A start has no deadline of its own: the test's or hook's timeout bounds it, and a start still waiting then writes its stderr to the output. CI installs the release pinned, with its SHA-256, in `.github/workflows/ci.yml`; locally, put that release, checksum-verified, on `PATH`. CI also lints `.github/workflows/` with actionlint, pinned with its SHA-256 in `ci.yml`; `pnpm check` does not run it.
- Tests that need SNS and SQS start their own `moto_server` from `PATH` with `packages/messaging/test/moto-server.ts`: a random local port read from the line it prints, its state reset between tests, owned as the NATS bullet says; never a fixed port or another emulator. CI installs moto from `packages/messaging/test/moto-requirements.txt` with `--require-hashes`, into a venv of the CPython `.python-version` pins, installed with its standard library compiled (`uv python install --compile-bytecode`), with the uv release pinned with its SHA-256 in `.github/workflows/ci.yml`; locally, install it the same way into a venv of that CPython and put `moto_server` on `PATH`. After changing `moto-requirements.in`, regenerate the `.txt` with the command its header names.
- The server's tests over TLS make a key and a self-signed certificate valid one day with `openssl` from `PATH`, into a temporary directory they remove (`packages/server/test/h2.ts`), so no private key is committed; they fail, never skip, without it. CI's runner image provides `openssl`, so `ci.yml` installs none; locally, the system's `openssl` serves.
- Changesets with one fixed group: every package releases together. Every PR that changes a package carries a changeset ([.changeset/README.md](.changeset/README.md)). cf-loom reaches 1.0.0 before any real Contract Package or Definitions Package publishes a version that is not a prerelease; before it, a real one is published only as a prerelease, with `cf-loom publish --prerelease`. The examples are not real packages: their acceptance test publishes them as any version, to the throwaway registry it starts.
- Published to npmjs.com as `@cf-loom/<name>`, with restricted access, from GitHub Actions: `.github/workflows/release.yml` publishes the changesets on `main`, and its header says how a version is released and what the organization sets up on npmjs.com and GitHub. The one exception is a placeholder `0.0.0` of each package, which an owner of the npm org publishes by hand once, since npm trusted publishing needs the package to exist.
- Commands: `pnpm build`, `pnpm test` (builds, then runs Vitest), `pnpm check` (Biome failing on warnings as CI does, the TSDoc check, the layout check, the terms check and, after a `pnpm build`, the expect-error check), `pnpm format`, `pnpm clean`, `pnpm changeset`.

## Design principles

- **Organization-agnostic.** cf-loom derives what follows from Contracts (Broker plans, reports, interfaces) and exposes it. Infrastructure and process policy (who applies Broker or gateway config, limits, permissions, review process) belongs to the organization: offer optional adapters, never defaults that impose a policy.
- **Shapes, not behavior.** A Contract declares shapes and declarative constraints only; nothing in it is implied or defaulted.
- **Can't prove it compatible, it's Breaking.** There is no warning level.
