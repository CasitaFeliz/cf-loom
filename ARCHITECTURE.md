# Architecture

How cf-loom's pieces fit. Terms are defined in [CONTEXT.md](CONTEXT.md); the rules for changing a Contract are in [COMPATIBILITY.md](COMPATIBILITY.md); how each package is used is in its README, listed in [README.md](README.md#packages), and a package's internal details are in the `ARCHITECTURE.md` next to that README.

## Tooling, not Contracts

- This repository holds the tools, and in `examples/` fictional Services and the Definitions Package they share, used as end-to-end tests. It contains no real Service's Contract.
- The tools know no organization: package names come from the package.json of whoever uses them, Approvers and how an Approval is enforced are their own review process, and the registry and its login are their own npm configuration, which the CLI uses through npm.
- Every Contract Package is published to the organization's npm registry; the tools are published to npmjs.com as `@cf-loom/<name>`, with restricted access.

## Packages

All packages are released together with one version. `zod` and `@cf-loom/contract` are peer dependencies of every cf-loom package and every Service's Contract Package, and every cf-loom package a cf-loom package uses is a peer dependency of it, so each process has one copy of each. What each package provides is listed in [Packages](README.md#packages) in README.md.

## Package layout

Every package under `packages/` lays out its `src/` the same way; a Service or a Definitions Package, such as the examples in `examples/`, follows [Layout](README.md#layout) in README.md instead; a Service may place its Handlers and generated files elsewhere with `layout` in `cf-loom.config.ts`, as billing-service does (see [The layout field](packages/cli/README.md#the-layout-field)):

- `src/` holds only entry files: the files the package's `exports` and `bin` point at in `dist/` (`index.ts` for `.`, `internal/index.ts` for `./internal`, one folder per subpath entry such as `node-http/index.ts`, and `bin.ts`), each named, never by a wildcard subpath, with its source file in `src/`, and beside each entry the tests that exercise it as a whole (`src/types.test.ts`). An entry folder holds its `index.ts` and those tests only. **(check)**
- An entry file holds named re-exports only, `export { … } from` and `export type { … } from`, or the empty `export {}` of a package not yet written (Biome's `noReExportAll` refuses `export *`), so an entry cannot grow logic; `bin.ts`, a CLI entry that calls the package's API, is the exception. **(check)**
- Every other file sits in a module folder named for its one responsibility, with an `index.ts` as the module's only seam; modules import each other only through it. **(check)**
- Modules form one direction of dependencies, listed in the package's own ARCHITECTURE.md; no cycles.
- No grab-bag folders (`utils`, `common`, `shared`, `helpers`; see C14 in [CODING_STANDARDS.md](CODING_STANDARDS.md)); a piece several modules need lives in the lowest module that owns its concept. **(check)**
- Modules are one level deep: a module that grows splits into sibling modules, not sub-folders. **(check)**
- Tests sit next to the file they test and import as [C23](CODING_STANDARDS.md#tests) says.
- Test support that several test files of a package share, such as a fake registry, sits in the package's `test/` folder, outside `src/`, so it is never built or published.

`scripts/check-layout.ts`, run by `pnpm check` and CI, enforces the rules marked (check); the direction of dependencies stays a review rule.

## Where Contracts live

- One Contract per package. Each Service and each Application keeps its Contract as plain source under `src/contract/` of its own package, whose root holds its package.json, and publishes it from there; that package may be a repository of its own (recommended) or one package of a monorepo. The Contract's files should import only each other, `zod`, `@cf-loom/contract`, Definitions Packages and the Contract Packages whose Elements it uses, so it builds and publishes on its own; cf-loom does not enforce it, and a Contract file that imports the Service's code runs that code on every cf-loom command. The CLI loads them and `cf-loom.config.ts` with Node's own type stripping, recording with a resolve hook which package each import resolved to, so they are erasable TypeScript whose relative imports name the `.ts` file (`./get-order.endpoint.ts`), in a package whose package.json has `"type": "module"`.
- A Contract is published as exactly one Contract Package carrying its Public and Internal Elements and its Snapshot. Its Dependencies are data in the Snapshot, never imports: a Contract Package depends on no other Contract Package. A Service's code is generated from its Snapshot, with Definitions Packages' schemas written in, so it depends only on `zod` and `@cf-loom/contract`, as peers; an Application's package has no code.
- The Snapshot also describes Private Elements, so they have a Baseline. Their shapes are readable by anyone with access to the registry; only their code stays out of the package.
- Applications publish a Contract that holds only Dependencies, so the registry records every use of a Service's Elements, an Application's included (see [Applications](packages/contract/README.md#applications) in the contract README).

## The Contract Package

`cf-loom package` generates the Contract Package's code from the committed declared Snapshot, and `cf-loom publish` generates it the same way, from the Snapshot with its `version` and history filled in (see [Where it lives](SNAPSHOT.md#where-it-lives) in SNAPSHOT.md), builds it with the project's own `tsc` in a temporary folder inside the project, and publishes it with the organization's npm, with no lifecycle script; no source file is bundled. It writes the zod schemas, the entry point and the package.json for the Public and Internal Elements that are not Retired, with the Guards, Rejections and recursive schemas they reach, as the exported Snapshot below says, plus the Snapshot itself. What is published is exactly what the Snapshot describes, and no Private code can leak into it:

```ts
// generated entry point of @org/contract-payments-service: each Element by its binding, nothing else
export { createPaymentEndpoint } from './endpoints/create-payment.ts';   // <name>Endpoint
export { getPaymentEndpoint } from './endpoints/get-payment.ts';
export { paymentSettledEventV1 } from './events/payment-settled.v1.ts'; // <name, first letter lower-cased>EventV<version>
export { paymentSettledEventV2 } from './events/payment-settled.v2.ts';
```

A Consumer imports the Elements it uses by name (`import { getPaymentEndpoint } from '@org/contract-payments-service'`), and the CLI records as `against` for their Provider the version in the package.json of the package that exports them (see [Dependencies](packages/contract/README.md#dependencies) in the contract README). The package.json declares `"sideEffects": false`, so a bundler drops every Element a Consumer does not import, and a browser bundle carries only the Endpoints its Dependencies list. Private Elements, Commands, Subscriptions and Dependencies are never exported. Schemas from Definitions Packages are written into the generated code and Dependencies are data in the Snapshot, so a Service's package.json declares only `@cf-loom/contract` and `zod`, as peers with the ranges [Versioning](COMPATIBILITY.md#versioning) gives, and every package.json carries the `cfLoom` metadata (see [Where it lives](SNAPSHOT.md#where-it-lives) in SNAPSHOT.md). How a peer's range moves the Contract Package's version is in [Versioning](COMPATIBILITY.md#versioning). The Service itself installs the Contract Packages it depends on as ordinary dependencies, since its client and Subscriptions use them.

The package is TypeScript built with `tsc` alone, since Node strips no types under `node_modules`: `package.json`, `snapshot.json`, a `tsconfig.json` with no Node or DOM types, since Applications import it in browsers, and under `src/` the entry `index.ts`, `standard-rejections.ts`, one file per exported Endpoint under `endpoints/`, per exported Event's Message Version under `events/` (`order-placed.v1.ts`), per Guard they reach under `guards/` and per code they answer under `rejections/`, the Standard ones excepted, and `defs.ts` when a schema reaches a recursive def. An Application's package is its `package.json` and `snapshot.json`, with no code, no build and no peers. Every package's `exports` name `./package.json` and `./snapshot.json`, which tooling reads by name. Its files are a function of the canonical Snapshot alone: every map is written in code point order. Each generated declaration is named for its kind, as [Modules](packages/cli/ARCHITECTURE.md#modules) in the CLI's ARCHITECTURE.md says, so no two generated names and no imported name meet; the entry re-exports each Element by that name and the types of the recursive defs it reaches.

Each exported Endpoint is a Provided Element, rebuilt from its Snapshot entry with `providedEndpoint`, which `@cf-loom/contract` exports for generated code, and carrying its Provider's Standard Rejections and the exported Snapshot cut to it: it marks the Endpoint as its Provider's, so a Group never lists it as the Service's own, and applies none of the type rules `defineEndpoint` applies to what an author writes, since a Reader schema breaks them. So `InputOf`, `SuccessOf` and `RejectionsOf` give a Consumer the Provider's types: its `input` as declared, the Guards' demands merged as the Snapshot records them, which is what the Service reads; its `success` headers and body and its Rejections' headers and bodies as Reader schemas, since the Consumer reads them; its Guards attached with their Qualifiers; and its own Rejections, the resolved codes but its Guards' and the two cf-loom's runtime adds, `notFound` as the Standard Rejection. Its Guards are rebuilt as declared, with their demands, Context, Qualifier schema and Rejections, and each Rejection with `providedRejection`, which marks nothing, since a Rejection is no Element. Each exported Event's Message Version is a Provided Element too, rebuilt from its Snapshot entry with `providedEvent`, its body a Reader schema, since its Subscribers read it, and its lifecycle as the Snapshot records it, left out when Active, so a Subscription to it type-checks. A Deprecated Endpoint's or Message Version's export carries a `@deprecated` tag with its description, so a Consumer's editor flags each use.

The exported Snapshot is the Snapshot cut to what the package exports: the Public and Internal Endpoints and the Internal Events that are not Retired, keyed by identity; the Guards the Endpoints attach and, through each Guard's `guards`, the Guards those build on; the codes those Guards answer and the Endpoints' own, the Standard Rejections' left to `standardRejections`; and the recursive defs any of their nodes reach, an Event's body included, keyed as in the Snapshot (see [Where it lives](SNAPSHOT.md#where-it-lives) in SNAPSHOT.md). `@cf-loom/contract` cuts it, and `cf-loom package` writes the package's code from it, so it never describes a Private Element's name or shapes. Each exported Endpoint carries the exported Snapshot cut to it: its entry, the Guards, codes and defs it reaches, no Events, and, under `shadowing`, every other declared Endpoint that wins a URL it matches, exported, Private or Retired alike, by identity and lifecycle alone, so a Fake Provider, given a request it matches, routes it as `serve` does. A Dependency keeps the Endpoints it lists with their cuts (see [Dependencies](packages/contract/README.md#dependencies) in the contract README), and the client and `fakeProvider` read from an Endpoint's cut, by the format it names, what no Reader schema says: the client the header names an Endpoint's Input declares and the nodes that convert a Success header from its text, the Fake Provider the nodes that convert a request's text parts, a Deprecated Endpoint's `deprecatedAt` and the Endpoints `shadowing` lists.

Reader schemas and types always come from a Snapshot, the same way for every Visibility, never from a type-level walk of the zod schema: a Contract Package's from its published Snapshot, for Dependencies, the invalid-input body's Reader included; a Service's own Events' that are not Retired and Commands' from its declared Snapshot, written by `generate` to the Readers file (`readers.generated.ts` by default), which also pairs each Command's Message Version and Subscription, imported from where it is exported, with the Reader its Message Handler reads, in its `readers` table, built by `readersOf`, which the Handler map carries so that `consume` reads every Message with the Reader the map pairs; a Retired Command's Reader and Pairing stay while it is declared, so its Handler compiles until it is deleted. Every object in them is open and every Open Enum has its Unknown case; their constraints and formats stay, so a value that breaks one is refused. An Open Enum's Reader is `openEnumReader`, a zod codec (see [Open Enums](packages/contract/README.md#open-enums) in the contract README). Their types are zod's output types of the generated schemas, written out only for a recursive def, so a type and its schema never disagree. The client's validation of what it receives (see [Consuming a Contract](packages/client/README.md#consuming-a-contract) in the client README), the Message Handlers (see [Message Handlers](packages/messaging/README.md#message-handlers)) and the Fake Providers of `@cf-loom/testing` (see [Faking Providers](packages/testing/README.md#faking-providers)) all use these generated Readers.

## Shapes, not behavior

- A Contract describes shapes and declarative constraints only: no defaults, transforms, refinements, coercion or custom validation (see [Not allowed in a Contract](COMPATIBILITY.md#not-allowed-in-a-contract)). What happens when an optional part of the Input is missing, and any check beyond a declarative constraint, belongs to the Handler and is expressed as a Rejection.
- The tooling validates what is written before sending it (Success, Rejections, Messages) and sends the parsed value, unknown keys stripped, so nothing carries an undeclared field; whoever reads a Success, a Rejection or a Message validates it with a Reader schema generated from the Snapshot, which ignores fields it does not know (see [The Contract Package](#the-contract-package)). Objects are open: a Contract declares no strict object (see [Not allowed](packages/contract/README.md#not-allowed) in the contract README). Open means an undeclared field is not refused, never that it is passed on: the Service reads its Input parsed, unknown keys stripped, as every reader does.
- Bodies are JSON. Binary bodies and streaming are not part of a Contract: an upload or a download goes through a pattern of the organization, such as signed URLs, or through a route outside the Contract (see [Endpoints](#endpoints)).

## Runtime

- The HTTP core speaks the web-standard Request and Response, so it also runs on Bun, Deno or inside another framework; an adapter connects it to a host, and cf-loom ships two: one for `node:http` and a Fastify plugin that serves a Contract beside the app's own routes (see [Adapters](packages/server/README.md#adapters)); Fastify is an optional peer dependency, installed only where its adapter is used.
- Messaging runs behind a Broker interface, the `Broker` type the messaging README documents, modeled on JetStream (see [Adapters](packages/messaging/README.md#adapters)), so an organization may write its own adapter; an adapter connects it to a Broker, and cf-loom ships one for NATS JetStream; `memory()` runs a Contract's messaging in memory, with no Broker, for tests. A Broker client is an optional peer dependency, installed only where its adapter is used.
- Testing support stays within what follows from Contracts: a Service's own code is tested through the exported functions of `@cf-loom/handlers`, and `@cf-loom/testing` builds Fake Providers only of other Services, checked against their Snapshots. Test runners, end-to-end tools and tests on a real Broker belong to the organization (see [Testing a Service's own code](packages/handlers/README.md#testing-a-services-own-code) and the [`@cf-loom/testing` README](packages/testing/README.md)).
- cf-loom reads a field plainly from a value its type declares, and through `ownOf`, or `isAbsentAt` for whether anything is at a path, from an `unknown`: what a Caller, a Handler, a body or a file hands it, which only the Contract gives a shape, read as JSON holds it, the properties the object holds itself. So a key a Contract names, a Guard's in a Context, an Element's in the Handler map or a declared header's among those given to `client()`, never reads one every object already has, which `generate` refuses too (see [Not allowed](packages/contract/README.md#not-allowed) in the contract README). A polluted `Object.prototype` is a broken process: zod, `Request` and `fetch` read through it, and cf-loom's runtime defends against it no more than they do. So is a schema changed under its `_zod` once zod built it, its `_zod.run`, a check's `_zod.check` or its def: `_zod` is zod's internal API, and `generate` and the runtime read a schema as zod built it, defending against such a change no more than zod does.
- An object of data or options whose shape cf-loom gives, never the Contract, such as an options object, what `fault()` is given or a Direct call's arguments beside its Input, demands or body, refuses in its type a field it does not declare, given as a literal or through a variable whose type is one object type, as a declaration does (see the [contract README](packages/contract/README.md)), and so does an object one of its fields holds whose shape cf-loom gives, such as a Direct call's `request` or a configuration's `layout`; so the runtime reads it as its type declares it, as it reads the Contract. A union whose members differ is refused only at a required parameter, and only in the fields it holds at the top; an upcast, an untyped value, or a nested object cf-loom does not name, such as the settings one stream or Durable consumer holds in `applyBrokerPlan`'s limits, is not refused in its type. `applyBrokerPlan`'s limits and a configuration are refused at run time, naming the field. An implementation of a cf-loom interface, such as a `Broker`, is no such object: it may hold more. A value whose shape the Contract gives, an Input part, a body, `{ headers, body }`, a Context, Resources, is open (see [Shapes, not behavior](#shapes-not-behavior)). So a function that forwards such an object types its parameter as the concrete type, `(map: HandlerMapOf<typeof contract, Resources>, options: ServeOptions<Resources>) => serve(contract, map, options)`, and a type parameter constrained to it, `<O extends ServeOptions<Resources>>(map: …, options: O) => serve(contract, map, options)`, is refused. The Handler map is not one: it stays open to keys the Contract does not name (see [Serving](packages/server/README.md#serving) in the server README). `success()`, `reject()` and `admit()` take their declaration first, so a literal is checked against it where it is written, and a variable may carry more, which the runtime strips.
- A Handler reaches what lies outside the Contract through the Resources the Service hands `serve` and `consume` at startup (see [Resources](packages/handlers/README.md#resources) in the handlers README).
- A Contract can be merged and deployed before its Handlers are implemented, with Stubs, and its Contract Package published; when it is published is the organization's (see [The Compatibility Check](COMPATIBILITY.md#the-compatibility-check) in COMPATIBILITY.md). How a Stub behaves is in [Stubs and the Handler map](packages/handlers/README.md#stubs-and-the-handler-map) in the handlers' README.
- A hook, `onServiceFault`, `onAnswered` or `onBrokerTrouble`, may be async; `serve` and messaging await it and ignore what it returns, and one that throws or rejects never escapes: the console gets `<source>: <hook> threw` with what it threw as cause, `serve` still sends its answer, and messaging leaves the Message for redelivery when `onServiceFault` failed, since it did not hear of it.
- Without an `onServiceFault` or an `onBrokerTrouble` (see [Serving](packages/server/README.md#serving) in the server README and [onServiceFault](packages/messaging/README.md#onservicefault) and [onBrokerTrouble](packages/messaging/README.md#onbrokertrouble) in the messaging README), `serve` and `messaging` write everything they would receive to the console: an Issue as its part, path, code and message, never the received value, a Fault as its message, or `the Handler threw`, and its `cause`, and a Durable consumer no longer pulled from, or answered again, as one line with the cause of its failure (the line `serve` writes is in [Serving](packages/server/README.md#serving) in the server README, those `messaging` writes in [onServiceFault](packages/messaging/README.md#onservicefault) and [onBrokerTrouble](packages/messaging/README.md#onbrokertrouble)).
- Every line a cf-loom library writes, an Error's message or each line of one that has several, and each line it writes to the console, is written with each line break inside it, each of CR, LF, VT, FF, FS, GS, RS, U+0085, U+2028 and U+2029, the characters Python's `str.splitlines` ends a line at, replaced by the visible text of its escape (`\r`, `\n`, `\u000b`, `\u000c`, `\u001c`, `\u001d`, `\u001e`, `\u0085`, `\u2028` and `\u2029`), so a key, a name, a path, an id or a message holding one never splits it; a message of several lines has one line per problem, joined by `\n`; what the console prints of a line's `cause` is the console's own. The CLI writes every line it prints the same way (see [What the commands print and write](packages/cli/README.md#what-the-commands-print-and-write) in the CLI README).

## Visibility and Guards

- Visibility is network reach only. A Command is always Private; an Event is Internal or Private; an Endpoint may be Public, Internal or Private.
- A Private Endpoint is called only by the owning Service's own processes or its infrastructure (for example a health check).
- Private Elements have no Consumers: the owning Service is never a Consumer of its own Contract. The compatibility rules protect Private Elements for the Releases running side by side.
- Authentication and authorization belong to Guards: a Public Endpoint may still require authentication.
- cf-loom does not enforce Visibility on the network: the organization enforces it with its gateway, ingress or network rules, or Visibility on HTTP stays a declaration.

## Endpoints

- An Endpoint declares its literal path and everything it requires. Groups only organize; they add no prefix and no Guards.
- When two Endpoints with the same method match one URL, routing precedence decides (see [Over HTTP](#over-http)).
- A Guard is attached explicitly, declared in the Contract or imported from a Definitions Package. A Guard may build on the Guards it lists and take a Qualifier from each Endpoint (see [Guards](packages/contract/README.md#guards) in the contract README). Each Service writes its own GuardHandler, even for an imported Guard.
- An EndpointHandler receives the Caller's Input; the Context its Guards provided and the request's signal and headers; and the Service's Resources, and answers an Outcome.
- A Service may serve routes outside its Contract. cf-loom does not see them: the Compatibility Check, Shadowing included, covers only declared Endpoints, so a new Endpoint that takes a URL an outside route served is the organization's to catch. Whatever splits requests between them, the host framework or a gateway, must send every declared Endpoint, Retired ones included, to cf-loom; `serve` hands every request no declared Endpoint matches to its `fallback` (see [Serving](packages/server/README.md#serving) in the server README); a framework adapter hands back what its fallback answers, and the Fastify adapter hands the app every request whose method and path no declared Endpoint has before `serve` sees it (see [Adapters](packages/server/README.md#adapters)).

## Messages

- Delivery is at least once and in no guaranteed order: once concurrency or redelivery is involved, nothing orders Messages across subjects or within one (`memory()` is sequential: see [In memory](packages/messaging/README.md#in-memory) in the messaging README). A Command is handled by one Message Handler, and every Handler must be safe to run again.
- Commands are their Service's own, always Private: they are in the Contract only so the compatibility rules protect Releases running side by side.
- A Service handles its own Events through Subscriptions, like any Subscriber.
- Where a Message travels is derived from the Contract (see [Over the Broker](#over-the-broker)). A Group adds nothing to a Message: its subject, Stream and Durable consumer never name it.
- cf-loom derives the Broker's desired state, the Streams and Durable consumers each Service needs, but never applies it on its own: when and how it is applied, retention, replicas and Broker permissions belong to the organization (see [The Broker plan](packages/messaging/README.md#the-broker-plan) in the messaging README), and so does whether the Broker enforces Visibility.
- **Deploy rule:** a Release that retires an Element is never deployed before the Release that deprecated it, nor before every Consumer has deployed the Release that stopped using it, by dropping the Endpoint from its Dependency or removing its Subscription to the Event; and a Release that retires a Command Version is deployed only once that version's Durable consumer has been drained by the Release that deprecated it (see [Leftover Durable consumers](packages/messaging/README.md#leftover-durable-consumers) in the messaging README). The tools do not know when a Release is deployed; this is an operating rule.

## Dependencies

- A Service or Application reaches a Provider only through a Dependency, which lists the Endpoints it calls, or a Subscription to an Event its Contract Package exports, both declared with the tools: a Dependency enables the typed client of those Endpoints, and such a Subscription enables a Message Handler Stub. Code cannot call what was not declared.
- A Service's Dependency targets only Public or Internal Elements; an Application's targets only Public Elements, since an Application runs outside the internal network.

## Wire protocol

How an Endpoint's Input and Outcome travel over HTTP, between `serve` and the client, and how a Message travels through the Broker.

### Over HTTP

- Bodies are JSON, sent as `content-type: application/json; charset=utf-8`, and what is sent is the parsed value, unknown keys stripped (see [Shapes, not behavior](#shapes-not-behavior)). A malformed body or a wrong content type is the invalid-input Rejection, with the `malformed` Issue code: a content type is right when its media type is `application/json`, whatever its parameters, and a body that is empty, no UTF-8 or no JSON, or whose stream fails while it is read, is malformed. A malformed body is answered alone, since the Input cannot be read, with the message "The content type is not application/json" or "The body is not JSON". The content type is read before the body, so a request that carries neither is "The content type is not application/json". A value nested too deeply to read, in any part of a request, a Success, a Rejection's body or a Message, is never a throw: it is one `malformed` Issue at the root of its part, with the message "The value is nested too deeply to read", beside the Input's other Issues, where a body that is no JSON is answered alone. `generate` reads an example and a Qualifier the same way: one zod cannot parse within the call stack is never a throw, but a value its schema refuses (see [Not allowed](packages/contract/README.md#not-allowed) in the contract README).
- A Provider reads a request in one order, the first step that fails answering alone: each attached Guard's demands, in Attachment order, its GuardHandler running once they are met and before the next Guard's are read; then the body, when the Endpoint declares one; then every part of the Input, whose Issues are answered together, the first of them listed within a fixed count and size (see [Rejections](packages/contract/README.md#rejections) in the contract README). The client and `fakeProvider` run no GuardHandler and read it as if every Guard admits the request; the client sends every part it read, its Guards' demands included.
- Path params, query params and headers, a Success's and a Rejection's included, travel as text and are converted to their declared types: a number matches `^-?(0|[1-9]\d*)(\.\d+)?$`, so it is written in plain decimal, never in exponent form (`1e21` travels as `1000000000000000000000`), and a boolean is exactly `true` or `false`; the values of one text part's enum each have a text of their own, so an enum of `1` and `'1'` fails `generate`; and each value's text is one its part can carry, so a header enum holding `' 1'` fails too. A list query param is a repeated key (`?id=a&id=b`), and one occurrence is a one-item list; a list with no items sends no key and reads as absent, so a required list cannot be sent empty; a repeated single-value key is handed to its schema as the list of its values, which refuses it as invalid input. A header given several times arrives as one comma-joined value (RFC 9110, section 5.3) and is converted as one text. A `+` in a query string is a space. A path param that fails its schema is invalid input, never the not-found Rejection. Headers of an HTTP response that the Endpoint does not declare pass through unread on both sides, other than cf-loom's own `Deprecation`, and `Retry-After`, which `serve` sends on a retryable Fault given `retryAfter` and the client exposes on any Fault. A path param, query param or header text holding a lone surrogate travels nowhere, since no UTF-8 can carry it. A header value travels only as RFC 9110 field text: a tab, visible ASCII, a space or U+0080 to U+00FF, with no whitespace leading or trailing; a Success or Rejection header that cannot is `INVALID_OUTCOME` (see [Validation](packages/server/ARCHITECTURE.md#validation) in the server's ARCHITECTURE.md).
- A declared header travels as given in every Caller's runtime, so cf-loom refuses, at `generate`, a header name a Caller's `fetch` owns and no configuration lets through: in a request, one the Fetch standard keeps for the user agent, which a browser drops or replaces and Node's `fetch` may refuse (`expect`) or replace (`sec-fetch-mode`); in a response, `set-cookie` and `set-cookie2`, which a browser never exposes to code. The names are in [Groups](packages/contract/README.md#groups) in the contract README.
- The request path is the URL's path as the [WHATWG URL Standard](https://url.spec.whatwg.org/) resolves it, the same on every host: dot segments, `%2e` included, are removed and `\` reads as `/`, so a path param's text is never `.` or `..`.
- Each path segment is percent-decoded on its own, so a decoded value never spans segments: `/orders/a%2Fb` is one param, `a/b`; a segment that is not valid percent-encoding is kept as sent. Under Fastify, which answers before any hook runs, two host exceptions apply: such a segment is Fastify's 400, and a param longer than its `maxParamLength` is its 414 when an app route shares the prefix. There is no trailing-slash or case folding, and an empty segment matches neither a literal nor a param, so `/orders/` and `//orders` match nothing; a request path matches a declared path exactly (see [Identities](SNAPSHOT.md#identities) in SNAPSHOT.md).
- Routing compares segment by segment, left to right: a literal beats a param at the first segment where they differ.
- An undeclared path is `NO_SUCH_ENDPOINT`, and a declared path with a method none of its Endpoints declares is `METHOD_NOT_ALLOWED`, with an `Allow` header listing those Endpoints' methods, Retired ones included; given a `fallback`, `serve` hands both to it instead. No Endpoint is `HEAD`: every Outcome but a Success travels in the response body, and a response to `HEAD` has none; `HEAD` on a declared path is therefore `METHOD_NOT_ALLOWED`, its body dropped by the host. `HEAD`, and `OPTIONS` and CORS preflight unless declared, are `METHOD_NOT_ALLOWED` on a declared path unless the `fallback`, the host, its adapter or the organization's gateway answers them first. CORS headers on an Endpoint's own response are added by whatever wraps the handler `serve` returns, never by `serve`. `nodeHttp` answers a method a web-standard `Request` refuses (`CONNECT`, `TRACE`, `TRACK`) with `NO_SUCH_ENDPOINT` before `serve` sees it, so it reaches neither the `fallback` nor the hooks. `fastifyServe` hands those of them that reach Fastify (`TRACE` and `TRACK`; Node hands `CONNECT` to the server's `connect` event, and over HTTP/2 answers it 405 when nothing listens), `HEAD`, an undeclared `OPTIONS` and any other method on a declared path to the app instead, so under Fastify they get the app's answer, never `METHOD_NOT_ALLOWED`.

A Rejection travels with its declared status, its declared headers and its Envelope, `{ rejection: { code, message, body } }`; a Rejection that declares no body has no `body` key. Rejection codes are open for Callers.

A Fault travels with its Envelope, `{ fault: { committed, retryable, message } }`, where `committed` is `'no'`, `'yes'` (done, but the Success was lost) or `'unknown'` (see [Fault](CONTEXT.md#language) in CONTEXT.md). `serve` answers it with 503 when it is retryable and 500 otherwise. The Reserved codes (see [Reserved code](CONTEXT.md#language) in CONTEXT.md) use the same body with a `code`, `{ fault: { code, committed, retryable: false, message } }`, which the client's Fault Outcome exposes:

| Code | Status | `committed` | Message | Answered when |
| --- | --- | --- | --- | --- |
| `RETIRED` | 410 | `'no'` | The Endpoint is retired | The Endpoint is Retired and still declared (see [Lifecycle](packages/contract/README.md#lifecycle) in the contract README) |
| `NO_SUCH_ENDPOINT` | 404 | `'no'` | No Endpoint has this method and path | No declared Endpoint has that path, and `serve` has no `fallback` |
| `METHOD_NOT_ALLOWED` | 405 | `'no'` | No Endpoint has this method on this path | A declared Endpoint has the path but none has the method, and `serve` has no `fallback` |
| `BODY_TOO_LARGE` | 413 | `'no'` | The body is too large | The body exceeds `maxBodyBytes` (see [Serving](packages/server/README.md#serving) in the server README) |
| `INVALID_OUTCOME` | 500 | `'unknown'` | The Outcome broke the Contract | The Handler's Outcome broke a constraint (see [Validation](packages/server/ARCHITECTURE.md#validation) in the server's ARCHITECTURE.md). The client produces the same code, with the status of the response it read, when a Success or a Rejection, its headers included, fails its Reader schemas; its `committed` depends on which (see [Consuming a Contract](packages/client/README.md#consuming-a-contract) in the client README) |

A response with the declared Success status is decoded as the Success, unless its body is no JSON, which is the inferred status Fault; a response whose body is a `{ rejection }` or `{ fault }` Envelope is decoded as such; anything else, or no response at all, becomes a Fault the client infers from what happened. A body is an Envelope when its media type is `application/json` and it is `{ rejection: { code, message, body? } }`, with a string `code` and `message`, or `{ fault: { committed, retryable, message, code? } }`, with `committed` one of its three values, a boolean `retryable` and a string `message`; other keys are ignored, and a Fault `code` that is not reserved is dropped. A Rejection Envelope's status is not checked against its code's. `client(deps, { inferFault })` replaces this inference (see [Consuming a Contract](packages/client/README.md#consuming-a-contract) in the client README):

| What happened (`source`) | Fault |
| --- | --- |
| `no-connection`: a DNS failure or a refused connection (a `TypeError` whose `cause.code` is `ENOTFOUND`, `EAI_AGAIN`, `ECONNREFUSED` or `UND_ERR_CONNECT_TIMEOUT`); `status` 429; `timeout` before the request was sent | `committed: 'no'`, `retryable: true` |
| `aborted` before the request was sent | `committed: 'no'`, `retryable: false` |
| `timeout` after it was sent (a `TimeoutError`, a signal aborted with one, or a `TypeError` whose `cause.code` is `UND_ERR_HEADERS_TIMEOUT` or `UND_ERR_BODY_TIMEOUT`); `connection-lost`, a connection lost after the request may have gone out (a `TypeError` whose `cause.code` is `ECONNRESET`, `UND_ERR_SOCKET`, `ETIMEDOUT`, `ENETUNREACH` or `EHOSTUNREACH`); `unreadable-body`, a body that fails while it is read; `status` 503 | `committed: 'unknown'`, `retryable: true` |
| `aborted` after it was sent (an `AbortError`, or a signal aborted with any other reason); `connection-failed`, any other `TypeError`; `status` of any other kind (500, 502, 504, a 3xx, 0, or the Success status with a body that is no JSON) | `committed: 'unknown'`, `retryable: false` |

- The client never follows a redirect: it sends every request with `redirect: 'manual'`, so a 3xx is decoded as any status but the Success's, and one with no Envelope becomes an inferred Fault; a browser hides a redirect behind status 0, inferred the same way.
- After a header function or `fetch` throws, after the Input is read, or after a body fails while it is read, a signal of the call that is aborted decides first: its reason named `TimeoutError` is a timeout, any other an abort, whatever was thrown. Errors are told by their `name`, never by their class, since each realm has its own.
- The `cause.code` values are Node's and undici's. Browsers and Deno report a refused connection or a DNS failure as a bare `TypeError`, which lands on the last row (see [In a browser](packages/client/README.md#in-a-browser-applications) in the client README); Bun's errors are not verified.
- An inferred Fault says one of five fixed messages, which carry nothing received: "No connection to the Provider" (`no-connection`), "The request was aborted" (`aborted`), "The request timed out" (`timeout`), "The connection failed" (`connection-lost`, `connection-failed` and `unreadable-body`) and "The Provider answered <status>" (`status`).
- Every Fault the client returns names its `source`: `provider` for an Envelope, `invalid-outcome` for the client's own `INVALID_OUTCOME`, else the kind of what happened above; and its `status` whenever a response arrived.

### Over the Broker

Where a Message travels follows from the Contract, so a Subscriber finds another Service's Events from its Contract Package alone: each Service that publishes or sends Messages owns one Stream named after it, and each Message Version has the subject `<service>.<event|command>.<Name>.v<version>` (`orders-service.event.OrderCreated.v2`). An optional Broker prefix, kebab-case of at most 64 characters as a Service name is, passed to the adapter at runtime and to `cf-loom broker-plan --prefix` and `cf-loom asyncapi --prefix`, goes in front of every subject, Stream and Durable consumer name (`staging.orders-service.event.OrderCreated.v2`, `staging_orders-service`), so several environments can share one Broker. Every Stream and Durable consumer name fits the 255 characters NATS allows, because the Broker prefix and the Service, Subscription and Message names they are made of have at most 64 characters each: the longest, a Subscription's Durable consumer `<prefix>_<service>_<name in kebab-case>`, has 64 + 1 + 64 + 1 + 95 = 225 (a 64-character name has at most 31 capitals, so its kebab-case adds at most 31 hyphens), a Command Version's `<prefix>_<service>_command_<Name>_v<n>` at most 220, and 72 is the largest cap under which every name fits.

On SNS/SQS a Stream is one standard SNS topic named as the Stream (SNS allows 256 characters), so a Subscriber finds its Provider's topic from the Contract Package alone, and a Message's subject travels in its `cf-loom-subject` attribute, which each Durable consumer's subscription filters on. Queue names are in [On SNS/SQS](packages/messaging/README.md#on-snssqs) in the messaging README.

On the wire a Message's body is the UTF-8 JSON of the Message body alone; the Message Version is in the subject, two headers carry the ids, `Nats-Msg-Id`, the Broker message id, `<event|command>.<Name>.v<version>:<factId>` (`event.OrderCreated.v2:o-1:created`), the subject after the Service's name and then the Fact id, so it is unique in the Service's Stream and the Broker drops only a repeated Message, and `Cf-Loom-Fact-Id`; the Transport headers travel as the Broker headers they were given (see [Publishing and sending](packages/messaging/README.md#publishing-and-sending) in the messaging README).

A Fact id and the Transport headers arrive as given on every Broker, so cf-loom refuses, before anything is sent, what NATS would act on, refuse or change:

- a Transport header named in cf-loom's `Cf-Loom-` or NATS's `Nats-` namespace, in any case, since JetStream acts on its own headers (`Nats-Expected-Stream` refuses a publish, `Nats-TTL` changes what is stored);
- a Transport header name NATS cannot carry: an empty one, which other NATS libraries drop, or one holding a `:`, a space, a control or a non-ASCII character, which nats.js refuses;
- a Fact id or Transport header value that would not arrive as given: one holding a CR or LF, which nats.js refuses; one with whitespace leading or trailing, as JavaScript's `trim` removes it, a no-break space and the other Unicode spaces included, which nats.js trims; or one holding a lone surrogate, which no UTF-8 can carry. A Fact id is never empty.
- a Fact id and Transport headers whose Broker headers would take more than the 65,535 bytes JetStream stores, which no configuration raises: counted as nats-core writes them, the `NATS/1.0` line, a `<name>: <value>` line for each header and the closing blank line, in UTF-8 bytes, with the Fact id counted twice, in `Cf-Loom-Fact-Id` and in `Nats-Msg-Id` after `<event|command>.<Name>.v<n>:`; each Message Version of a call is measured with its own Broker message id, and one that does not fit refuses the whole call.

Anything else travels as given: any other character of a value, an empty value, and two names that differ only in case, which are two headers.

How large a whole Message may be, its body included, is the organization's NATS configuration (`max_payload`, which counts the headers too, and a Stream's `max_msg_size`), and so are the headers NATS adds when the organization turns them on, such as message tracing or a Stream's sources; cf-loom refuses only what no configuration lets through. `publish` sends a call's largest Message first (see [Publishing and sending](packages/messaging/README.md#publishing-and-sending)), so a Message too large for either limit is refused before any of its call is sent.

Read back from the Broker, a Message's ids are the values of `Nats-Msg-Id` and `Cf-Loom-Fact-Id`, and its Transport headers are the headers named outside the `Cf-Loom-` and `Nats-` namespaces, in any case, the several values of one name joined with `, `; any other header in those namespaces, the two ids' names in another case among them, is neither an id nor a Transport header. A Message lacking either id, or with one the Fact id's rule refuses, an empty one among them, was not published by cf-loom and is never handled.
