# @cf-loom/messaging

`messaging`, which connects a Contract's messaging through a Broker: EventPublisher, CommandSender, `consume` for Subscriptions and Commands, `close`; the errors `InvalidMessageError`, `MessageNotSentError` and `MessagingClosedError`; and its types, `ConsumeOptions` and the `Broker` an adapter implements among them (see [Types](#types)). `@cf-loom/messaging/jetstream` is its adapter for NATS JetStream, `jetstream` and its types, `JetStreamBrokerOptions`, `JetStreamBroker`, `BrokerPlan` and `BrokerLimits` among them, and `@cf-loom/messaging/memory` an in-memory one for tests and local development, `memory` and its types (see [Adapters](#adapters)). What the Broker must hold, and how the adapter applies it, is in [The broker plan](#the-broker-plan), [Applying the plan](#applying-the-plan) and [Leftover durable consumers](#leftover-durable-consumers); how a Message travels is in [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker) in the root ARCHITECTURE.md. Terms are defined in [CONTEXT.md](https://github.com/CasitaFeliz/cf-loom/blob/main/CONTEXT.md).

The examples follow the layout in [A first Service](https://github.com/CasitaFeliz/cf-loom/blob/main/README.md#a-first-service) and leave out imports of the Contract's declarations.

## Connecting

`messaging(contract, broker)` connects through the Broker and resolves to one connection's `Messaging`, `{ publisher, sender, consume, close }`; a Broker that fails to connect rejects it. `src/main.ts` connects it with the organization's Broker adapter (see [Serving](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/server/README.md#serving) in the server README, which both example Services follow with the JetStream one), a test with the in-memory one (see [In memory](#in-memory)), and hands its `publisher` and `sender` to the Handlers as Resources, through `serve` and `consume` (see [Resources](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/handlers/README.md#resources) in the handlers README). Each `messaging()` is its own connection: connecting again is calling it again. The Service connects at startup so a broker problem, a missing stream or durable consumer included (see [Applying the plan](#applying-the-plan)), fails there rather than inside a request. `consume(handlers, { resources })` hands each Message Handler the Resources and hands the Broker its consumers once per `Messaging`: consuming twice throws, and a `consume` the Broker rejects may be called again. The Service calls `close()` at shutdown, which stops consuming, waits for the Handlers running and for every `publish`, `send` and `consume` in flight, from whichever caller, and closes the connection the moment nothing is in flight: while it waits, publishing and sending still work, and are waited for too, so a Handler running can finish, and a Message delivered meanwhile is left pending, its Handler never run. Calling `close()` again returns the same promise; consuming rejects with `MessagingClosedError`, `messaging is closing`, while it waits, and once nothing is in flight, publishing, sending and consuming reject with `MessagingClosedError`, `messaging is closed`. Broker options come from the Service; cf-loom has no defaults for them.

`messaging(contract, broker, { onServiceFault })`, which may be async, receives what Message Handlers end or fail with, a `ConsumedFault` whose `element` is the Subscription or the Command's Message Version and whose `identity` names it (`notifyOnSettled`, `ChargeCard@1`), with the Message's `subject`, `messageId` and `factId`, and the delivery's `deliveryCount` and `lastAttempt`, whether the Broker will not deliver it again: `invalid-body`, a Message ended for failing its schema, with its `issues`; `returned`, a Fault the Handler returned, retryable or not, as `fault`; and `thrown`, anything thrown, as `cause`. Without an `onServiceFault`, they go to the console, one line per issue, `<identity> <subject> <messageId> <factId> attempt <n>: body.<path> <code>: <message>`, or one line, `<identity> <subject> <messageId> <factId> attempt <n>: ` and the Fault's message or `the Handler threw`, with its `cause`; the last attempt reads `attempt <n>, the last` (see [Runtime](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#runtime) in the root ARCHITECTURE.md).

`messaging(contract, broker, { onBrokerTrouble })`, which may be async, receives a `BrokerTrouble` when a durable consumer stops being pulled from, once, with its `element`, `identity`, `durable`, `stream` and the `cause` (`pull-failed`), and once when its pulls are answered again (`recovered`); `durable` and `stream` are unprefixed, as `connect` gives them. A connection closed for good is `pull-failed` with no `recovered` after, and reconnecting, through the Service's own `connect` and a new `messaging()`, is the Service's. Without it, each goes to the console as one line, `<identity> <durable> <stream>: pulls are failing` with its cause, or `<identity> <durable> <stream>: pulls are answered again`; an `onBrokerTrouble` that throws or rejects is logged as `<identity> <durable> <stream>: onBrokerTrouble threw`. A readiness probe needs only the hook, `onBrokerTrouble: (t) => t.kind === 'pull-failed' ? failing.add(t.identity) : failing.delete(t.identity)`; what the Service does is the organization's.

## Publishing and sending

```ts
// in a Handler taking { publisher } as Resources, once the order is committed
const { duplicates } = await publisher.publish(
  'OrderCreated',
  { v1: { orderId, total: total.amount }, v2: { orderId, total } },   // v1 Deprecated, still published
  { factId: `${order.id}:created` },
);
// in a Message Handler, chaining from the Message it handles
await sender.send('ChargeCard', { orderId }, { factId: `${meta.factId}:charge`, headers: { traceparent: meta.headers['traceparent'] } });
```

`publish` takes an Event's name and one body for each of its Active and Deprecated versions, whatever Groups its versions sit in: leaving one out, or passing a Retired one, is a type error, so adding a new Message Version flags every place that publishes the Event; publishing an Event whose `version` is typed `number`, which keys no body, is a type error too. `send` takes a Command's name and sends its one Active version. Both validate every body of the call with its version's schema before any leaves, and send the parsed value; a body that breaks it is refused with `InvalidMessageError` (see below), each such version listed by its identity with its `issues` at `body`, and nothing is sent. `publish` sends the versions in version order.

Every call takes a Fact id, which all its Messages share and every Message Handler receives to recognize a fact it already handled: a non-empty string that arrives as given on every Broker (see [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker) in the root ARCHITECTURE.md). The calling code derives it from the fact: from the committed entity, or in a Message Handler from the Message it handles (`meta.factId`), so a retry or a redelivery sends the same id and the Broker drops the copy; a random id would send the fact again.

`headers` are transport headers, `traceparent` for one, an `undefined` one left out: opaque strings cf-loom passes to the Broker unread and hands to every Message Handler in its meta (see [Message Handlers](#message-handlers)). They are not part of the Contract and never validated against a schema, but one that would not arrive as given on every Broker is refused, a name in cf-loom's `Cf-Loom-` or NATS's `Nats-` namespace among them, in any case, and so are a Fact id and transport headers that together take more than the 65,535 bytes JetStream stores in a Message's headers (see [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker) in the root ARCHITECTURE.md). `publish` and `send` reject with `InvalidMessageError`, whose `invalid` lists each part refused, all at once, the Fact id (`factId`), each transport header (`headers.<name>`), each version whose headers are too large, then each body, one line each in its message, and send nothing.

Each Message is sent with its broker message id (`event.OrderCreated.v2:o-1:created`, see [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker)), so the Broker drops a duplicate within its deduplication window. The Fact id also travels in its own header, `Cf-Loom-Fact-Id`, and is never parsed out of the id. `publish` resolves to `{ factId, duplicates }`, the identities of the versions the Broker already held and dropped, and `send` to `{ factId, duplicate }`: a duplicate is the expected outcome of a retry, or of a Fact id reused for another fact, which the calling code may log. If the Broker fails, `publish` and `send` reject with a `MessageNotSentError` that names the Fact id (`factId`) and the versions already sent (`sent`, `OrderCreated@1`, always empty for `send`), with the Broker's error as `cause`, and the Handler retries the whole call with the same Fact id: versions already sent are dropped as duplicates. How long the window lasts is the organization's broker configuration; beyond it, Handlers still recognize the fact by its id. Publishing within the transaction that commits the change (an outbox) is the organization's.

## Message Handlers

```ts
// src/subscriptions/orders/notify-on-settled.handler.ts
import { readers } from '../../readers.generated.ts';

export default handle(
  readers.subscriptions.notifyOnSettled,
  async (body, { messageId, factId, deliveryCount, headers }, { resources: { notifications } }: Needs<'notifications'>) => {
    await notifications.send(body.paymentId);
  },
);
```

`readers.subscriptions.notifyOnSettled` is the Subscription as a Message Handler takes it, from the readers file (see [Testing a Service's own code](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/handlers/README.md#testing-a-services-own-code) in the handlers README). A CommandHandler has the same shape, and `Needs` is the Service's own (see [Resources](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/handlers/README.md#resources) in the handlers README). Delivery is at least once (see [Messages](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#messages) in the root ARCHITECTURE.md). Returning nothing acknowledges the Message. Throwing, or a Fault with `retryable: true`, leaves it unacknowledged, so the durable consumer's configuration (ack wait, backoff, max deliveries), the organization's, decides when it comes again and what happens after the last attempt, and both reach `onServiceFault`; `deliveryCount` tells the Handler which attempt this is, and `lastAttempt` whether the Broker will not deliver it again, so the Handler may record the fact before it is dropped. A Message Handler's Fault, `MessageFault`, takes no `retryAfter`: the durable consumer's configuration decides when the Message comes again. A Fault with `retryable: false` ends it (JetStream `term`): no redelivery, and it is logged. Returning anything else counts as a throw. `headers` are the transport headers the Message was published with (see [Publishing and sending](#publishing-and-sending)). How the adapter keeps a slow Handler's Message from another process of the Service meanwhile is in [In-progress acknowledgements](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/messaging/ARCHITECTURE.md#in-progress-acknowledgements).

Messages are validated with the generated Reader schemas (see [The Contract Package](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#the-contract-package) in the root ARCHITECTURE.md): another Service's Event with its Contract Package's, the Service's own with the readers file. `consume` reads each Message with the Reader of the pairing the Handler map's `readers` hold for its Subscription or Command's Message Version, which its Handler must be written for, and throws before it pulls from any, naming the key and saying `run cf-loom generate`, when the map has no Handler there, holds one written for another declaration or for another pairing than its `readers` hold, or its `readers` lack the pairing. A Message that fails its schema, or whose body is no UTF-8 JSON, never reaches the Handler: it is ended without redelivery and logged with its subject, its ids and the issues (see [Serving](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/server/README.md#serving) in the server README for what a log carries); where it goes next is the organization's broker configuration.

## Adapters

An adapter is a `Broker` (see [Types](#types)): `connect` receives the Service's stream and the subjects of the Messages it publishes and sends, unprefixed, and returns the connection `messaging` publishes, consumes and closes through, so an organization on another Broker may write its own. The core computes every subject, stream and durable consumer name unprefixed, and the adapter adds the prefix; an `OutgoingMessage`'s `messageId` is the id the Broker deduplicates by, and the connection's `publish` resolves to `{ duplicate }`, whether the Broker dropped the Message as one it already held; each `BrokerConsumer`, `{ durable, stream, subject, receive }`, names its durable consumer, and its `receive` runs its Handler and resolves to the `Settlement` the adapter applies, `'acked'`, `'ended'` (JetStream `term`) or `'pending'`, left for redelivery; `receive` resolves even when `onServiceFault` throws or rejects: the core logs that and answers `'pending'`; `consume` receives the consumers and `{ closing, troubled }`: `closing` is a signal the core aborts the moment `close()` starts; `consume` resolves once consuming has started and rejects having started nothing, and once `closing` aborts, or if it already has, it hands nothing more to `receive`, a Message still handed over being left pending by the core; it calls `troubled` once when a consumer stops being pulled from, with the cause, and once when its pulls are answered again, never once `closing` has aborted, and `troubled` returns at once; `close` is called once nothing is in flight: Handlers running, `publish`, `send`, `consume` and trouble reports, which the core keeps, not the adapter, and it ends what `consume` started and finishes applying any Settlement.

The interface assumes JetStream semantics: the core refuses what NATS would not carry as given (the `Cf-Loom-` and `Nats-` header namespaces, the 65,535 bytes of broker headers), and relies on the Broker dropping a repeated `messageId` within its deduplication window and reporting it, on a delivery count per Message, and on acknowledging, ending and leaving a Message for redelivery as JetStream `ack`, `term` and no acknowledgement do; an adapter for another Broker provides the same or documents what differs.

### JetStream

`jetstream({ connect, prefix, jetstream })` from `@cf-loom/messaging/jetstream` connects to NATS JetStream, as `src/main.ts` does in [Serving](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/server/README.md#serving) in the server README. The option `connect` is the Service's own function that opens a NATS connection, with the transport and authentication the Service chooses (`connect` from `@nats-io/transport-node`, for one); cf-loom calls it once for each `messaging()` and once for each `apply`, and drains each connection it opened: a `messaging()`'s at `close`, an `apply`'s when it ends. Its NATS packages, `@nats-io/jetstream` and `@nats-io/nats-core`, are optional peer dependencies (see [Runtime](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#runtime) in the root ARCHITECTURE.md); keep every `@nats-io/*` package on one version, since `@nats-io/jetstream` pins `@nats-io/nats-core` exactly. `prefix` is in [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker) there, and `jetstream` is nats.js's own JetStream options, a JetStream domain, an API prefix or a request timeout, which cf-loom hands to its JetStream client and manager unchanged, with no defaults of its own except `checkAPI: false` on the manager, so no `$JS.API.INFO` is requested. What `jetstream()` returns, a `JetStreamBroker`, is a `Broker` that also has `apply`, which applies the broker plan (see [Applying the plan](#applying-the-plan)); `apply` rejects with an error naming the stream or durable consumer it could not apply, with the client's error as `cause`, where `messaging()` rejects with it unchanged. `jetstream()` throws on a `prefix` that is not kebab-case, `''` included: leave it undefined for none. `messaging()` rejects with the error the Service's `connect` rejected with, or, once connected, when the Service's stream does not exist, naming it, or does not hold every subject it publishes and sends, naming the stream and each subject it does not hold, after draining that connection; any other error of that check, such as JetStream not enabled, rejects it unchanged, after the same drain. NATS decides whether a stream holds a subject, so a stream made with a wildcard holds it. Each Message is published with its broker headers and waits for the Broker's acknowledgement; a duplicate acknowledgement counts as sent and is reported as `duplicate`. `close` drains the connection, and resolves when it is already closed, or waits for a drain the Service started. The NATS subjects `messaging()` uses are `$JS.API.STREAM.NAMES`, requested for that check, and the Service's prefixed subjects, which it publishes on and whose acknowledgements come back through the connection's inbox; the Service's NATS permissions must allow them.

`consume` asks NATS for the prefixed durable consumer of each Subscription and Command Version whose Handler it pulls before it pulls from any, and rejects, pulling from none, with a line for each thing wrong, naming it: a durable consumer that does not exist, with the stream it reads; a stream that does not exist, with the durable consumer that reads it; and a durable consumer that is not a pull consumer with explicit acknowledgements, filtered on its subject, delivering whole Messages and with no priority groups, with what differs. Any other error of that check, such as an unknown JetStream domain, rejects it unchanged. A `consume` that was rejected may be called again once the plan is applied (see [Applying the plan](#applying-the-plan)).

Each durable consumer hands its Handler one Message at a time, pulling the next only once the last is settled, so no Message waits in the Service. Each pull is a request for one Message on a subscription of its own that expires after 30 seconds, or after the durable consumer's `max_expires` when that is shorter, read at `consume` like the waits. The Service's durable consumers run side by side, and several processes of the Service pull from the same durable consumer, its `maxAckPending` capping them all. A Message reaches its Handler as [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker) in the root ARCHITECTURE.md reads it back, with NATS's delivery count as `deliveryCount`; `lastAttempt` is true when the delivery count reaches the durable consumer's `max_deliver`, read at `consume` like the waits, and with no limit it is never true. `acked` acknowledges a Message (JetStream `ack`), `ended` ends it (`term`), and `pending` leaves it to NATS. A Message without `Nats-Msg-Id` or `Cf-Loom-Fact-Id`, which cf-loom never publishes, is ended by the adapter itself with the reason `no <header> header`, which NATS's termination advisory carries, and nothing reaches `onServiceFault`; watching the advisories is the organization's. While its Handler runs, cf-loom sends the Message in-progress acknowledgements every third of that delivery's wait (see [In-progress acknowledgements](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/messaging/ARCHITECTURE.md#in-progress-acknowledgements)); the waits are read from the durable consumer at `consume`, so a changed ack wait or backoff reaches a running Service the next time it consumes.

When `close()` starts, cf-loom drains the subscription of the pull that is open instead of dropping it, so a Message published meanwhile stays on its durable consumer for the next consumer, and every Message the Broker had already sent arrives and is handed back (`nak`) for another process of the Service, none left to wait out its ack wait. A pull NATS answers with an error, as when a durable consumer is deleted, or does not answer within twice its expiry, as when publishing on the pull's subject is not permitted, is tried again a second later; the first such failure and the first answer after it reach `onBrokerTrouble` (see [Connecting](#connecting)), so consuming resumes once the durable consumer exists again and the Service hears of both. A connection that closes for good while consuming ends pulling, and each durable consumer reports `pull-failed` once. A durable consumer recreated in another shape is checked at the next `consume`. The NATS subjects `consume` uses are `$JS.API.CONSUMER.INFO` and `$JS.API.CONSUMER.MSG.NEXT` for each prefixed stream and durable consumer, and the acknowledgement subjects `$JS.ACK.<stream>.<durable consumer>.>`, or `$JS.ACK.<domain>.<account hash>.<stream>.<durable consumer>.>` where NATS writes the longer form, with a subscription on the connection's inbox for each pull; the Service's NATS permissions must allow them.

### In memory

`@cf-loom/messaging/memory` is a broker adapter that keeps everything in memory, for tests and local development:

```ts
import { messaging } from '@cf-loom/messaging';
import { memory } from '@cf-loom/messaging/memory';
import { contract } from '../src/contract/index.ts';
import handlers from '../src/handlers.generated.ts';
import createOrderHandler from '../src/endpoints/orders/create-order.handler.ts';

const broker = memory();
const running = await messaging(contract, broker);
const resources = { publisher: running.publisher, sender: running.sender };
await running.consume(handlers, { resources });

await createOrderHandler({ body: newOrder }, { apiKey: { callerId: 'c-1' } }, { resources });
await broker.settled();   // OrderCreated v1 and v2 published, ChargeCard v1 sent and handled
broker.messages;          // each with its subject, body, Fact id, broker message id and transport headers

await broker.deliver(payments.events.paymentSettledV1, body, { factId: 'pay-1' });
// → 'acked' | 'pending' | 'ended'

await running.close();
```

- **Delivery.** What the Service publishes or sends is delivered to its consumed Subscriptions and CommandHandlers, acknowledged or ended as `consume` does; an Event that two Subscriptions take reaches each, in the order `consume` was given them. A Message nothing consumes, because no Subscription takes the Event, its Handler is a stub or it was published before `consume`, is only recorded.
- **Order.** Delivery is sequential, in publish order, which production never guarantees (see [Messages](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#messages) in the root ARCHITECTURE.md). `publish` and `send` resolve once the Message is recorded, before its Handlers run.
- **`settled()`** waits until nothing is in flight, including Messages that Handlers publish or send while it waits. It rejects if a Handler threw or returned a Fault, a Message was ended, an `onServiceFault` threw or rejected or deliveries were cut (see **The cut**) since the last `settled()`, so a failure cannot pass a test unnoticed. The error's message has one line per failure: the console's lines (see [Connecting](#connecting)), `<identity> <subject> <messageId> <factId> attempt <n>: onServiceFault threw` for an `onServiceFault` that threw or rejected, after the Fault's lines, and `a chain of Messages was cut after 1,000 deliveries` for a cut. Its `cause` is the first failure's `ConsumedFault`; a cut carries none. A failure is reported once.
- **The cut.** Deliveries are counted since nothing was last in flight, whether or not they form a chain, and the 1,001st is cut: a chain of Handlers that keep producing Messages, 1,001 concurrent `deliver`s and a `redeliver()` of 1,001 pending Messages alike. The Messages still waiting are never delivered: one the Service published or sent stays in `messages` and is not added to `pending`, one a `deliver` injected is in neither, and a pending one stays in `pending` at its `deliveryCount`; a `deliver` or `redeliver()` still waiting rejects with the cut's error.
- **`deliver(message, body, meta?)`** delivers one new Message now, as attempt 1, whatever was delivered before, so a test can deliver the same fact twice to check that a Handler is safe to run again. It takes an Event or a Command Message Version: an Event reaches every consumed Subscription to it, a Command its CommandHandler, and it resolves to the most severe settlement, `'ended'` before `'pending'` before `'acked'`. It joins the line behind the Messages already lined up. Its body is written as a Subscriber reads it, like `fakeEvent`'s (see [Faking Events](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/testing/README.md#faking-events) in the testing README), written back through each consumer's Reader as a direct call's is (see [Testing a Service's own code](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/handlers/README.md#testing-a-services-own-code) in the handlers README): a body that breaks a Reader rejects with `InvalidInputError` at `body`, and nothing is delivered. `meta` is `{ factId?, messageId?, headers? }`: the Fact id is random when left out, the broker message id defaults to `<event|command>.<Name>.v<version>:<factId>`, and `headers` are the transport headers the Handler receives, `{}` when left out. A Fact id or transport header `publish` would refuse is refused as it refuses it, with `InvalidMessageError` (see [Publishing and sending](#publishing-and-sending)), and so is a broker message id the Fact id's rule refuses, at `messageId`, or one that takes the Message's headers past what JetStream stores. Delivering a Message Version nothing consumes, because no Subscription takes the Event, its Handler is a stub, it is Retired or `consume` was not called, rejects, naming it.
- **Redelivery.** The adapter never redelivers on its own: a Message whose Handler threw or returned a retryable Fault stays in `broker.pending`, listed for the Subscription or Command it is pending for, until `redeliver()` delivers every pending Message again, each to that consumer alone, as attempt `deliveryCount + 1`; acknowledged or ended, it leaves the list. A Message that fails again waits for the next `redeliver()`, and one that left the list meanwhile is skipped. `redeliver()` resolves once the Messages it lined up have settled, and `settled()` covers the Messages their Handlers publish; each call is its own pass, so two calls made together can deliver the same Message. A Message left pending while messaging closes is listed too. After the connection is closed, `deliver` and `redeliver` reject. Each Message in `pending` is listed as `{ element, identity, subject, messageId, factId, deliveryCount, headers, body }`, `element` the Subscription or the Command's Message Version and `identity` its name, as in a `ConsumedFault`, its body the wire JSON, as in `messages`.
- **Duplicates.** A repeated broker message id from `publish` or `send` is dropped and reported as a duplicate, neither recorded in `messages` nor delivered, for the adapter's whole lifetime.
- **Not a broker emulator.** It models nothing of the organization's broker configuration (deduplication window, redelivery limits, backoff, retention), so `lastAttempt` is always false, and has no `apply`; tests against a real Broker remain the organization's. One `memory()` serves one connection: a second `messaging()` through it rejects, even after the first is closed.

## The broker plan

`cf-loom broker-plan` (see [Commands](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/cli/README.md#commands) in the CLI README) prints the desired state of one Service from its committed `contract.snapshot.json`, offline: the Service's stream, which holds the subject of each of its Events' and Commands' Message Versions that are not Retired, and which a Service that publishes and sends nothing does not have; each Subscription's durable consumer and the stream it reads; and each durable consumer of a Command Version that is not Retired (`orders-service_command_ChargeCard_v1`, which no Subscription's durable consumer can collide with, its name in kebab-case holding no `_`). `--json` prints it on one line in a fixed shape, shown here across lines, with names and subjects in code point order, so the organization's own tooling can read it; with a prefix, every subject, stream and durable consumer name carries it, and `service`, a Service's name, never does:

```json
{
  "prefix": null,
  "streams": {
    "orders-service": { "service": "orders-service", "subjects": ["orders-service.command.ChargeCard.v1", "orders-service.event.OrderCreated.v1", "orders-service.event.OrderCreated.v2"] }
  },
  "consumers": {
    "orders-service_command_ChargeCard_v1": { "service": "orders-service", "stream": "orders-service", "subject": "orders-service.command.ChargeCard.v1" },
    "orders-service_notify-on-settled": { "service": "orders-service", "stream": "payments-service", "subject": "payments-service.event.PaymentSettled.v1" }
  }
}
```

## Applying the plan

Nothing applies it by default (see [Messages](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#messages) in the root ARCHITECTURE.md); the organization applies it with the `apply` of what `jetstream()` returns, in a deploy step, or from its own infrastructure tooling. `apply` is no part of `Broker` (see [Types](#types)): `messaging()` never applies anything.

```ts
import { connect } from '@nats-io/transport-node';
import { jetstream } from '@cf-loom/messaging/jetstream';

const broker = jetstream({ connect: () => connect({ servers: process.env.NATS_URL }), prefix: process.env.BROKER_PREFIX });
await broker.apply(plan, limits);   // creates and updates, never removes
```

`plan` is the JSON above, as `cf-loom broker-plan --json` prints it; `apply` refuses one of another shape, and one whose `prefix` is not the one `jetstream()` was given. `limits` holds every setting cf-loom has no opinion on, keyed by the names the plan prints: for each stream `retention` (`limits`, `interest` or `workqueue`), `maxAge`, `duplicateWindow`, `replicas` and `storage` (`file` or `memory`); for each durable consumer `deliverPolicy` (`all`, `new`, `last` or `last_per_subject`), `ackWait`, `maxDeliver` and `maxAckPending`; `streamDefaults` and `consumerDefaults` fill in whatever a stream or durable consumer does not set. A duration is a whole number from 1 and one unit, `ms`, `s`, `m`, `h` or `d` (`500ms`, `30s`, `2m`, `7d`), one NATS can hold exactly: its nanoseconds fit 64 bits and a JavaScript number, so `365d` is fine and `106752d` is not; `maxAge`, `maxDeliver` and `maxAckPending` also take `'unlimited'`; `replicas`, `maxDeliver` and `maxAckPending` are otherwise whole numbers from 1. `ackWait` is one duration, or one for each delivery, the last repeating, which NATS calls a backoff. An `undefined` value for one of these settings, or an `undefined` entry for a stream or durable consumer, means the same as leaving it out. Before it connects, `apply` refuses a setting left unset, a setting `limits` does not have, a stream or durable consumer name the plan does not list, and a value that is none of these, naming each, so it creates and changes nothing. For example:

```ts
await broker.apply(plan, {
  streamDefaults:   { retention: 'limits', maxAge: '7d', duplicateWindow: '2m', replicas: 3, storage: 'file' },
  consumerDefaults: { deliverPolicy: 'all', ackWait: ['30s', '1m', '5m'], maxDeliver: 5, maxAckPending: 100 },
  streams:   { 'orders-service': { replicas: 1 } },
  consumers: { 'orders-service_notify-on-settled': { ackWait: '2m' } },
});
```

`apply` only creates streams and durable consumers, adds subjects and updates limits; it never removes anything, so applying a newer plan never takes away what an older Release still running consumes: applying is safe before the new Release deploys and while the old one runs. A stream gets each subject of the plan it does not hold yet, NATS deciding as for `messaging()`'s check, so a stream made with a wildcard gets none; a durable consumer is a pull consumer with explicit acknowledgements, filtered on the plan's subject, that delivers whole Messages and has no priority groups, its filter set through `filter_subject`, so one filtered through `filter_subjects` is changed to it; on a stream or durable consumer that exists, a NATS setting `limits` has no name for, such as `max_bytes`, stays as it is. `apply` creates the plan's streams before its durable consumers, each in the plan's order, and stops at the first it cannot apply, keeping what it created or updated: a durable consumer whose stream does not exist yet, naming the stream, or one NATS refuses, such as a stream whose storage or a durable consumer whose deliver policy or ack policy would change, or a push consumer that would become a pull consumer, which NATS never does, naming the stream or durable consumer, with NATS's error as `cause`; a Provider's plan is applied before its Subscribers', and when two Services subscribe to each other's Events, applying the first again after the second completes it. A Release fails fast when the plan was not applied: `messaging()` checks that the Service's stream exists and holds every subject it publishes or sends, and a Service that publishes and sends nothing has none to check, `consume` that the durable consumer of every Subscription and Command Version whose Handler it pulls exists, as a pull consumer with explicit acknowledgements, filtered on its subject, that delivers whole Messages and has no priority groups, and each fails with an error naming what is missing. `apply` opens its own connection and drains it when it ends; the NATS subjects it uses are `$JS.API.STREAM.INFO`, `$JS.API.STREAM.CREATE`, `$JS.API.STREAM.UPDATE` and `$JS.API.STREAM.NAMES`, and `$JS.API.CONSUMER.INFO` and `$JS.API.CONSUMER.CREATE`, for the plan's names, which the NATS permissions of whoever applies it must allow.

## Leftover durable consumers

cf-loom never removes a durable consumer. A prefix holds no `_` (see [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker) in the root ARCHITECTURE.md), so `<prefix>_<service>_` names one Service of one environment; on a Broker where one Service runs with a prefix, every Service runs with one, or a Service named as a prefix would read that environment's durable consumers as its own. A Service's durable consumers are all named `[<prefix>_]<service>_…`, on its own stream or on its Providers' (see [The broker plan](#the-broker-plan)), so those a removed Subscription or a Retired Command Version left behind are the ones under that name that the Service's plan does not list. The organization finds and deletes them with its own tooling, once no running Release consumes them and, for a Command Version, once its durable consumer is drained (see the deploy rule in [Messages](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#messages) in the root ARCHITECTURE.md). Rolling back to a Release that consumed a deleted one needs that Release's plan applied again.

## Types

- `Messaging`, `{ publisher, sender, consume, close }`: one connection's messaging, what `messaging()` resolves to.
- `MessagingOptions`, `{ onServiceFault?, onBrokerTrouble? }`: what is operational about messaging and no part of the Contract.
- `ConsumeOptions<Resources>`, `{ resources }`: what `consume` takes besides the Handler map, the Resources its Message Handlers take.
- `EventPublisher` and `CommandSender`: `publish` and `send`, typed by the Contract's Events and Commands.
- `MessageOptions`, `{ factId, headers? }`: what a `publish` or `send` call carries besides its bodies.
- `Published`, `{ factId, duplicates }`, and `Sent`, `{ factId, duplicate }`: what `publish` and `send` resolve to.
- `ConsumedFault`: what `onServiceFault` receives, with `element`, the Subscription or the Command's Message Version, `identity`, its name, and the delivery's `deliveryCount` and `lastAttempt`: `invalid-body`, `returned` or `thrown`.
- `BrokerTrouble`: what `onBrokerTrouble` receives, with `element`, `identity`, and the unprefixed `durable` and `stream`: `pull-failed` with its `cause`, or `recovered`.
- `InvalidMessageError`, with `invalid`, its `InvalidPart`s, `body` with a version's `identity` and `issues`, `id` with `at`, `header` with its `name` and `fit`, and `too-large` with a version's `identity` and `bytes`: what `publish` and `send` reject with when the call breaks a rule, and `deliver` for a refused id, header or header bytes.
- `MessageNotSentError`, with `factId` and `sent`: what `publish` and `send` reject with when the Broker failed.
- `MessagingClosedError`: what `publish`, `send` and `consume` reject with once messaging is closed, and `consume` while it is closing.
- `Broker`, `{ connect }`: what `messaging()` connects through, an adapter's or the organization's own; `BrokerService`, `{ stream, subjects }`, what it tells the Broker: the Service's stream and the subjects of the Messages it publishes and sends, unprefixed.
- `BrokerConnection`, `{ publish, consume, close }`: one connection to a Broker; `publish` resolves to a `BrokerAck`, `{ duplicate }`; `consume` takes the consumers and a `ConsumeRun`, `{ closing, troubled }`: the signal the core aborts when `close()` starts, and where the adapter reports a `ConsumerTrouble`, `{ consumer, kind }`, `pull-failed` with its `cause` or `recovered` (see [Adapters](#adapters)).
- `OutgoingMessage`, `{ subject, messageId, factId, headers, body }`: a Message as it leaves, its body the UTF-8 JSON bytes.
- `BrokerConsumer`, `{ durable, stream, subject, receive }`: the durable consumer of a Subscription or Command Version whose Handler is pulled, and `receive`, which runs that Handler.
- `Delivery`, `{ messageId, factId, deliveryCount, lastAttempt, headers, body }`: one Message as an adapter hands it to `receive`.
- `Settlement`, `'acked'`, `'pending'` or `'ended'`: what the adapter does with a delivery.
- `MemoryBroker`, `{ connect, settled, messages, deliver, redeliver, pending }`: what `memory()` returns, a `Broker` a test drives and watches.
- `RecordedMessage`, `{ subject, messageId, factId, headers, body }`: a Message as the in-memory Broker took it, its body parsed from its JSON.
- `DeliveryMeta`, `{ factId?, messageId?, headers? }`: what `deliver` may set.
- `PendingMessage`, `{ element, identity, subject, messageId, factId, deliveryCount, headers, body }`: a Message a consumer left unacknowledged, its body the wire JSON.
- `JetStreamBrokerOptions`, `{ connect, prefix?, jetstream? }`: what `jetstream()` takes, the Service's own function that opens a NATS connection, the prefix and the options of nats.js's JetStream client.
- `JetStreamBroker`, `{ connect, apply }`: what `jetstream()` returns, a `Broker` that also applies a broker plan.
- `BrokerPlan`, `{ prefix, streams, consumers }`, with `BrokerPlanStream`, `{ service, subjects }`, and `BrokerPlanConsumer`, `{ service, stream, subject }`: the plan `cf-loom broker-plan --json` prints.
- `BrokerLimits`, `{ streamDefaults?, consumerDefaults?, streams?, consumers? }`, with `StreamLimits`, `{ retention, maxAge, duplicateWindow, replicas, storage }`, `DurableConsumerLimits`, `{ deliverPolicy, ackWait, maxDeliver, maxAckPending }`, and `Duration`: what `apply` takes besides the plan.
