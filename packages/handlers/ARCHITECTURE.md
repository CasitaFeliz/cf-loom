# Internals of @cf-loom/handlers

How the package's `src/` is split into modules, as [Package layout](../../ARCHITECTURE.md#package-layout) in the root ARCHITECTURE.md requires. The entries `src/index.ts` (`.`) and `src/internal/index.ts` (`./internal`) re-export from the modules' `index.ts`.

## Modules

| Module | Holds | Depends on |
| --- | --- | --- |
| `outcomes/` | `success`, `reject`, `admit`, `fault`; the built and resolved Outcome and Admission types, `Fault`, and `Committed` and `Internal error` from `@cf-loom/contract`'s `wire/`; the runtime shapes, telling an Outcome, an Admission or a Fault by its kind and fields | none |
| `checks/` | what a call is given and what a Handler built, part by part with `schemaOf`, against the schemas of its Endpoint or Guard, and that a Success's headers can travel as text, by the wire rule in `@cf-loom/contract`, as Issues with their part; a Message body written back through and read with its Reader schema, and a received Message body read with it alone; the resolution of a Rejection against the Standard Rejections | `outcomes` |
| `calls/` | running one call: check what it is given, run the implementation, check what it built; a return that is no Outcome, or anything thrown while running or checking what it built, is the Fault with its `cause`, and anything thrown while checking what it is given is that Fault with `committed: 'no'`, so a run never throws, and `notRunFaultOf` builds that Fault for `serve` too, for a throw while it reads a request; `InvalidInputError`, `InvalidOutcomeError` and the direct call's answer, which throws on them; running one call of a Message Handler, where a throw stays a throw and a return is nothing or a Fault, and the `MessageMeta` a Message Handler receives; one Issue as a line of an error or a log, which `serve` and `messaging` write too | `checks`, `outcomes` |
| `handlers/` | `handle`, `handle.stub`, `withReader`, the Handler types and `HandlerMap`; what a Handler was written with, its stub mark included, hidden from its call signature; `runEndpoint`, `runGuard`, `runMessage`, `readerOf`, `isStub` and `mappedHandlerOf` for `./internal` | `calls`, `checks`, `outcomes` |

## The runtime's seam

A Handler is a function carrying its `element`, the Endpoint or Guard it was written for; what it was written with sits beside it, out of its type, so `serve` takes Handlers of every Endpoint or Guard through one parameter type. `./internal`'s `runEndpoint` and `runGuard` run the same call as a direct call and return how it went as a value for `serve` to answer: `invalid-input`, `invalid-outcome`, `thrown` (a throw, or a return that is no Outcome, as the Fault with its `cause`; a throw while checking what the call is given is not committed, since the implementation never ran) or `answered`, a Fault the Handler returned included; `serve` alone sends `thrown`, `invalid-outcome` and a returned Fault to `onServiceFault`. Inside `serve`, an Issue at `context` or `qualifier` is the runtime's own bug, since `serve` builds both: it answers it as a Fault and reports it to `onServiceFault`. A direct call is that run plus a throw on the two invalid kinds. `runMessage` runs a Message Handler on a body as `consume` received it, read with its Reader and never written back, as a direct call's body is, and `readerOf` gives that Reader. `mappedHandlerOf` is the map check `serve` and `consume` share: the Handler the map holds as its own under a key, which `handle()` returned for that very Element, or a throw naming the key, `endpoints.getOrder` or `commands.chargeCardV1`; `serve` runs it for every Handler in the map before the first request, `consume` before it pulls.
