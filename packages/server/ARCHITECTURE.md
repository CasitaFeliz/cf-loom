# Internals of @cf-loom/server

How `serve` (see [README.md](README.md)) answers a request and validates what it sends, and how the package's `src/` is split into modules, as [Package layout](../../ARCHITECTURE.md#package-layout) in the root ARCHITECTURE.md requires. How an Outcome travels over HTTP, routing and text conversion included, is in [Over HTTP](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-http) in the root ARCHITECTURE.md.

## Modules

The entry `src/index.ts` (`.`) re-exports from `answering/`, `src/node-http/index.ts` (`./node-http`) from `node-host/`, and `src/fastify/index.ts` (`./fastify`) from `fastify-host/`, whose types alone import `fastify`. The modules of `.` import no `node:` module, so `serve` runs wherever its host runs.

| Module | Holds | Depends on |
| --- | --- | --- |
| `served/` | what `serve()` prepares once: each declared Endpoint with its segments, lifecycle, Handler, Attachments with their Handlers and Qualifiers, and `deprecatedAt`, the walked text nodes by declaration, the resolved Standard Rejections, the body limit and the Resources it hands every run; the startup failures it throws, naming the Endpoint or Guard, or the value of a `maxBodyBytes` that is no limit, its Handler lookups through `@cf-loom/handlers`'s `mappedHandlerOf` | none |
| `answering/` | `serve` and its types; one request top to bottom; the Guards' runs plugged into the contract's reading, each with its Context, Qualifier and the Resources; a run's kinds as a `Response`, the code it sends and a `ServedFault`, a Rejection as built resolved against the Root's Standard Rejections, the invalid-input Rejection answered in one place, and the runtime's own bug; the hooks, each awaited and contained, and their console fallback; a request no declared Endpoint matches handed to the `fallback`, and an `Http` that rejects answered with the internal Fault, which `serve`'s fallback and `nodeListener` share; `servingOf`, `serve`'s handler with the Endpoints it matches, for an adapter that decides before `serve` | `served` |
| `incoming/` | an `IncomingMessage` or `Http2ServerRequest` read as a web-standard request: its URL by one set of target and `Host` rules, an HTTP/2 request read as the absolute-form target its `:scheme`, authority and path make, or why it has none, its `Request`, held from the signal it follows, the take's, so a Handler that keeps only the signal still sees it abort, its headers without pseudo-headers and with one `Cookie`, its body read from the message only when the `Request`'s body is read, a chunk per read, so a body nobody reads stays Node's to end, over HTTP/2 a body whose stream is reset or whose connection is lost before the Caller's END_STREAM failing its read, since Node ends the request on every close and marks it aborted, and the 400 that answers a request that cannot be read | none |
| `outgoing/` | a request an adapter took from its host, with its protocol's steps chosen once by the class of its response, and the Caller's departure as one signal: over HTTP/1.1 aborted at once when the response is already closed unfinished, else when it closes so, over HTTP/2 when the stream is reset or its connection lost before the response ended; it holds what follows it until the take ends, releasing it after its last chance to abort; a `Response` written to it, the one writer both adapters use and the one containment region after the take: the answer awaited, status and headers, each replacing one the host set before, a `content-length` the host set dropped, a body written as it is read and framed by Node, over HTTP/1.1 by the length the Response states, else chunked, its `drain` wait and its stream's cancel both ending with the Caller's signal; a body read only in part cut off, over HTTP/1.1 by `connection: close`, over HTTP/2, when its Caller has not sent END_STREAM, by resetting the stream with `NO_ERROR` once the response's END_STREAM is sent, which Node marks only in the stream's state, polled, backing off to once a second, until the stream closes; over HTTP/1.1 the socket destroyed when anything after the request is taken fails, over HTTP/2 no `connection` header and a failure resetting the stream with `INTERNAL_ERROR` | none |

| `fastify-host/` | `fastifyServe`: a Fastify plugin whose global `onRequest` hook hands the app every request no declared Endpoint has, by `allowedMethodsOf`, before building a `Request`; takes every other one from Fastify with `reply.hijack()` before `serve` runs and hands `outgoing` its `Response` to write to `reply.raw`, with the headers earlier app hooks set; refuses a prefix and an encapsulated plugin at registration; serves HTTP/1.1 and HTTP/2 apps, `allowHTTP1` included, each request by its own version | `answering`, `incoming`, `outgoing` |

The request and response sides are free of Handlers and hosts and live in `@cf-loom/contract`'s `wire/`, with the other wire rules the client and `@cf-loom/testing` share: matching a request to an Endpoint and reading its text parts and body, text conversion, building a `Response` from a Success, Rejection or Fault, the invalid-input Rejection's included, the Reserved codes with their texts, the `Deprecation` header and the invalid-input body. The order a request is read in lives in the contract's `reading/`. The runs of the Handlers live in `@cf-loom/handlers`'s `./internal`. `serve` keeps answering, the hooks, the startup check and the two adapters.

## A request

1. The method and the decoded segments are matched against every declared Endpoint, Retired ones included: none is `NO_SUCH_ENDPOINT`, another method on a declared path `METHOD_NOT_ALLOWED`, either handed to the `fallback` when there is one; a Retired one `RETIRED`.
2. The contract's reading reads the request in the order of [Over HTTP](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-http) in the root ARCHITECTURE.md. Each GuardHandler runs with its demands as the reading parsed them, the admitted Context of the Guards it lists, the Endpoint's Qualifier for it and the request's signal and headers, then the Resources; a body too large is answered alone, unread; a value nested too deeply to read is the invalid-input Rejection, like any other Input that breaks the Contract.
3. The EndpointHandler runs with the Input as the reading parsed it, the admitted Context of the Guards the Endpoint attaches and the request's signal and headers, then the Resources, and what it answered is sent, a Rejection with the code, status and message the Root resolves and the headers it declares; a Deprecated Endpoint's response, whatever it is, carries the `Deprecation` header.
4. A `ServedFault` goes to `onServiceFault`, then the request's record to `onAnswered`, each with the Request, awaited and contained.

An Issue at `context` or `qualifier` means `serve` built something the Contract refuses: it is the runtime's own bug, answered as a Fault not committed and reported as `runtime-bug`, never as the Caller's invalid input.

## Validation

The Handler's run in `@cf-loom/handlers` checks every Success and every Rejection, their declared headers included, before `serve` sends it, the checks a Direct call runs ([Testing a Service's own code](../handlers/README.md#testing-a-services-own-code) in the handlers README). A header value that cannot travel as text (see [Over HTTP](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-http) in the root ARCHITECTURE.md) is an Issue at `success.headers`, or at `headers` for a Rejection's, with its name as path and the code `invalid_format`. The run also checks a Fault's `retryAfter`: one that is no whole number of seconds from 0, or that sits on a Fault that is not retryable, is an Issue at `fault`, with the path `retryAfter` and the code `invalid_value`. A Handler's Outcome that type-checks but breaks a constraint is never sent: the Caller receives a Fault with `INVALID_OUTCOME`, `committed: 'unknown'` and `retryable: false`, and the validation Issues go to the Service, never to the Caller (see `onServiceFault` in [Serving](README.md#serving)).
