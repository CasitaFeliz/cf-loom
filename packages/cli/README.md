# @cf-loom/cli

The `cf-loom` command, `defineConfig` and its types `Config` and `Layout` (see [Configuration](#configuration)); how its `src/` is split into modules is in [ARCHITECTURE.md](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/cli/ARCHITECTURE.md). Terms are defined in [CONTEXT.md](https://github.com/CasitaFeliz/cf-loom/blob/main/CONTEXT.md); the Compatibility Check the command runs is in [COMPATIBILITY.md](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md), and the Snapshot it writes in [SNAPSHOT.md](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md).

## Configuration

A Service that places its Handlers and generated files elsewhere than the defaults configures the tools in `cf-loom.config.ts`, next to its package.json: at the root of its repository, or in its own directory of a monorepo, where the CLI runs. The file is optional, and a project without it takes every default. The CLI reads its `config` export; it is never part of the Snapshot or the published package. Like the Contract's files, it is erasable TypeScript (see [Where Contracts live](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#where-contracts-live) in the root ARCHITECTURE.md).

```ts
// cf-loom.config.ts
import { defineConfig } from '@cf-loom/cli';

export const config = defineConfig({
  layout: {                          // a Service only; each field is optional
    endpoint: 'src/billing/{name}.handler.ts',
    handlerMap: 'src/generated/handlers.generated.ts',
  },
});
```

`defineConfig` takes a `Config` and returns it, so a misspelled field, in it or in its `layout`, is a type error as [Runtime](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#runtime) in the root ARCHITECTURE.md says. `layout`, a `Layout`, is the one field of a `Config`, optional and a Service's only (see [The layout field](#the-layout-field), whose table has a field of `Layout` in each row); any other field fails. `check` and `publish` read the registry through npm (see below); `generate`, `verify`, `package`, `broker-plan`, `openapi` and `asyncapi` run offline.

cf-loom reads and publishes through the `npm` on your `PATH`, run in the project's directory with its environment, so the registry and the login are your npm configuration, exactly as for installing: `@org:registry=` or `registry=` and an auth token in an `.npmrc` (the project's, yours, or one `NPM_CONFIG_USERCONFIG` names) or in `npm_config_*` variables. cf-loom has no registry or login setting of its own. `publish` packs the staged package with `npm pack <folder> --ignore-scripts`, reads that tarball as it reads a Baseline's (see below), and runs `npm publish <tarball> --tag <tag> --ignore-scripts` there, so the bytes it read are the bytes npm publishes: `latest` for the version that becomes the Baseline, that is every version that is not a prerelease, and a prerelease while cf-loom published none that is not one; else `next`. So the package always has the `latest` dist-tag `npm view` needs to list its versions. No lifecycle script of yours runs, and npm's `tag` setting and a `publishConfig.tag` are overridden: `--tag` is always given, and a Definitions Package's `publishConfig.tag` is left out of what is published, the rest of its `publishConfig` kept. Right before it runs `npm publish`, `publish` lists the package's versions again and exits 3 when it lists a version it did not list at the first read, since the Check never judged against it, so a version is not published against a Baseline that is no longer the one; rerun it, which reads the registry again. The Baseline is the highest version `npm view` lists that cf-loom published and that is not a prerelease, else the highest prerelease it published (see [The Baseline](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#the-baseline) in COMPATIBILITY.md). The version the Compatibility Check compares with is the Baseline, or with `check --against` the one it names; its `cfLoom` and peer ranges come from `npm view`, which `check` and `publish` also run for each version they try before the Baseline and pass over for lacking `cfLoom`, and only its tarball is downloaded, with `npm pack`, to read `snapshot.json`; cf-loom requires the tarball to hash to a sha512 that `npm view` lists for the version. A package npm cannot find counts as never published only when `npm whoami` reports a user on the registry that serves the package's scope, or `registry=` for an unscoped package; a login that cannot read the package also looks unpublished, so the printed line names the registry and the user. A package none of whose versions has a `cfLoom`, such as npm's `0.0.0` placeholder or a package that adopts cf-loom at `3.2.0`, has no Baseline either: its first version is 1.0.0, or the next major above the highest version it lists that is not a prerelease. Any npm error, a package that lists no version or has no `latest` dist-tag (which `npm view` needs to list them), a package whose versions were all unpublished, a version `--against` names without `cfLoom`, a `cfLoom` with no kind, a Baseline of another kind, a tarball without a sha512 integrity or that does not hash to it, a tarball with a tar entry that `npm pack` does not write, such as a link or a GNU long name, or with a path that is not printable ASCII (0x20 to 0x7E) or holds a `:` or a `\`, such as a file named with an accented letter (cf-loom reads `snapshot.json` out of the tarball by hand, as `npm pack` writes tarballs for printable-ASCII paths without `:` or `\`, and refuses anything else, since npm could unpack it differently), or a `snapshot.json` that cannot be decoded fails with exit 3, and so does `publish` of a package whose own tarball is such a tarball, such as one that holds a file named with an accented letter or a `Snapshot.json` beside its `snapshot.json`, before it runs `npm publish`, since that version would fail every later `check` and `publish`. So does a package npm cannot find when the registry that serves it, its scope's `@org:registry=` or else `registry=`, holds a user and password in its URL, which npm will not print: put them in a `//host/:_authToken` or `//host/:_auth` line instead. A registry URL in a printed line never carries a user or password.

A Contract Package is named after the project's package.json: `<scope>/contract-<name>`, or `contract-<name>` for an unscoped package. A Definitions Package is published under its package.json's name. The CLI records, with a resolve hook around the Root's import, which installed package each of the Contract's imports resolved to, so a Definitions Package is the module the Root holds, of any scope. A Contract Package `cf-loom package` writes is `0.0.0` in its package.json, so a Service that installs it, as a workspace does, records `against: '0.0.0'`, and the origins of its Definitions Packages read the workspace's versions; only `publish` derives a version. `publish` exits 3 on any version of another package that the Contract is declared against, a Dependency's `against` or a Definitions Package version an origin names, that the registry does not list (a package it does not know included), and `check` prints the same lines on stderr and exits by its Changes. A Dependency's `against` is the version in the package.json of the installed Contract Package that exports its Provider's Elements, found as a Definitions Package is, by identity among the packages the Root's files import.

### The layout field

A Service places its Handler files, and the two files `generate` regenerates, with `layout`: each field is a path from the project's directory, written under `src/`, and a field left out keeps its default. `generate` writes the Stub of each Handler at its path, the Handler map imports the Handlers from there, and `verify` compares the files there.

| Field | Places | Variables | Default |
| --- | --- | --- | --- |
| `endpoint` | an Endpoint's Handler | `{group}`, `{name}` | `src/endpoints/{group}/{name}.handler.ts` |
| `guard` | a Guard's Handler | `{name}` | `src/guards/{name}.handler.ts` |
| `command` | a Command's Handler, one per Message Version | `{group}`, `{name}`, `{version}` | `src/commands/{group}/{name}.v{version}.handler.ts` |
| `subscription` | a Subscription's Handler | `{group}`, `{name}` | `src/subscriptions/{group}/{name}.handler.ts` |
| `handlerMap` | the Handler map | none | `src/handlers.generated.ts` |
| `readers` | the Readers file | none | `src/readers.generated.ts` |

A path may hold the variables its field takes, each written in braces. `{group}` is the name of the Group that lists the declaration; `{name}` is the declaration's name in kebab-case, as files are named (`getOrder` is `get-order` and the Command `ChargeCard` is `charge-card`); `{version}` is the Message Version's number. With `endpoint: 'src/billing/{name}.handler.ts'`, the Endpoint `getOrder` has its Handler at `src/billing/get-order.handler.ts`.

A path that breaks one of these rules stops every command that reads the config with exit 3:

- It starts with `src/`, not `src/contract/`, which holds only the Contract.
- A Handler's path ends with `.handler.ts` and a generated file's with `.generated.ts`, so a formatter that skips `*.generated.ts` skips what `verify` compares, wherever the layout puts it; no folder ends with either.
- Each segment is not empty, does not start with a dot, and its text outside the variables holds only lower-case letters, digits, `-`, `_` and `.`: paths are portable, and two names never differ by case alone. A file name holds no `.d.`, which TypeScript reads as a declaration file.
- It holds only the variables its field takes in the table.
- `handlerMap` and `readers` are two files.

Two declarations at one Handler path fail `generate` and `verify` (exit 3), naming both, a path being one file whatever link leads to it: a `command` path without `{version}` fails while a Command declares two Message Versions that are not Retired. A Handler path that, once filled, breaks a rule above, such as a file name holding `.d.` once `{name}` is `d`, or `src/{group}/{name}.handler.ts` for a Group named `contract`, or that a link leads out of `src/` or into `src/contract/`, fails `generate` and `verify` too (exit 3), naming its declaration; so does a `handlerMap` or `readers` path that a link leads there. An Application or a Definitions Package has no Handlers, so a `layout` in its config fails with exit 3.

`generate` and `verify` claim no `*.handler.ts` by its path: the Handler map on disk, and any file `generate` wrote that is left at a path the layout no longer names, record every Handler cf-loom imports and the declaration each one serves. A recorded Handler that the layout now places elsewhere is moved there by `generate`, which prints `Moved <old> to <new>`; one whose declaration is Retired or no longer declared, or whose new path already holds a file, or whose path `generate` could not have placed, because it breaks a rule above or because a link leads it out of `src/` or into `src/contract/`, fails `generate` and `verify` (exit 1) with the line saying what to decide, naming the file that imports it, and nothing is moved or written until none stands; so a changed `layout`, a changed default, a renamed Group or a renamed declaration never leaves an implemented Handler behind a fresh Stub. Any other `*.handler.ts`, such as a Lambda's, is yours, under every layout. A `*.generated.ts` under `src/`, outside `src/contract/`, that starts with `// Generated by cf-loom generate. Do not edit.` at neither `handlerMap` nor `readers` is the record `generate` reads before it writes, unless a link leads it out of `src/` or into `src/contract/`, in which case it is never read, moved from or deleted; `generate` deletes it once the new files are written, printing `Deleted <path>`, and `verify` fails on it (exit 1). Inside the layout only `generate` places a file: what its lines ask of you is to delete a file or to move it off its path, never to put one at a path the layout names. To keep a gone Handler's code for the declaration that replaces it, move the file off its path, run `generate`, which writes the replacement's Stub and prints `Wrote <path>`, and put the code there. Move no Handler to a path the layout names and delete no generated file by hand: the Handler map names the old paths until `generate` rewrites it, so a path one Handler leaves and another takes cannot be told apart after a hand move, and a deleted map leaves nothing to move from.

## Commands

Every command takes `--json`, which prints one JSON document on stdout instead of its lines (see [--json](#--json)).

| Command | Does |
| --- | --- |
| `cf-loom init [service \| application \| definitions]` | Creates the Root, `src/contract/index.ts` (or `src/definitions/index.ts`) exporting `contract`, `application` or `definitions`, a Service's or Application's named after package.json without its scope, a name that must be kebab-case of at most 64 characters; with no kind, a Service's. It never overwrites a file, and only appends to `.gitattributes` the lines `contract.snapshot.json text eol=lf` and `*.generated.ts text eol=lf` that it lacks, creating it when there is none, so Git keeps the line endings `generate` writes, which `verify` compares byte for byte. A project has one Root: the one its Root file exports, under any name |
| `cf-loom --help`, `-h`, `help [<command>]`, `<command> --help` | Prints the usage of the CLI, or of the one command named, and exits 0 |
| `cf-loom --version` | Prints `@cf-loom/cli <version> (Snapshot format <n>)`, the Snapshot format it writes, and exits 0 |
| `cf-loom generate` | Writes `contract.snapshot.json`, overwriting a committed file that is out of date or no JSON, and stopping at one in a newer format than this cf-loom reads (see [Where it lives](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#where-it-lives) in SNAPSHOT.md); for a Service it also regenerates the Handler map (its Handlers and the Readers file's `readers`), typed `satisfies HandlerMapOf<typeof contract>`, and the Readers file, `src/handlers.generated.ts` and `src/readers.generated.ts` unless the [layout](#the-layout-field) places them, moves each Handler the Handler map imported to where the layout now places it, deletes each file it wrote that is left at a path the layout no longer names, and writes the Stub of every missing Handler (see [Stubs and the Handler map](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/handlers/README.md#stubs-and-the-handler-map) in the handlers README), while an Application or a Definitions Package gets `contract.snapshot.json` only, and `generate` and `verify` import only its Root, not every file beside it, so none of the checks on what a file exports applies to it. It fails on an Endpoint, attached Guard, Command's Message Version or Subscription that nothing exports (no file under `src/contract/`, or its Definitions Package's entry), on an Endpoint, Event, Command's Message Version or Subscription that a file under `src/contract/` exports and no Group lists, on a Group such a file exports that the Root does not list, on a Handler the Handler map imported whose declaration is Retired or gone, or whose new path already holds a file, on a Handler path that is no file, on a Handler path that breaks the layout's rules once filled or that a link leads out of `src/` or into `src/contract/`, on a `handlerMap` or `readers` path that a link leads there, on a Handler that a file `generate` wrote imports at a path `generate` could not have placed, and on two declarations at one Handler path, and then writes nothing |
| `cf-loom broker-plan [--prefix <p>] [--json]` | Prints the Streams and Durable consumers the Broker must hold for a Service, from the committed `contract.snapshot.json`, which must be what `generate` would write, as for `package`; it reads neither the registry nor the Broker (see [The Broker plan](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/messaging/README.md#the-broker-plan) in the messaging README); an Application or a Definitions Package has none |
| `cf-loom openapi` | Prints an OpenAPI 3.1 document of every Endpoint of a Service as JSON, from the committed `contract.snapshot.json`, which must be what `generate` would write, as for `package`; it reads neither the registry nor the Broker, and writes no file: redirect it, `cf-loom openapi > openapi.json`. See [openapi](#openapi) for what it writes of each Endpoint, and [JSON Schema](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#json-schema) in SNAPSHOT.md for its schemas. An Application or a Definitions Package has none |
| `cf-loom asyncapi [--prefix <p>] [--broker jetstream\|sqs]` | Prints an AsyncAPI 3.1 document of every Event of a Service that is not Retired as JSON, from the committed `contract.snapshot.json`, which must be what `generate` would write, as for `package`; it reads neither the registry nor the Broker, and writes no file: redirect it, `cf-loom asyncapi > asyncapi.json`. `--prefix` puts the prefix in front of every address, as for `broker-plan`. `--broker` names the Broker whose wire the document describes: `jetstream`, the default, or `sqs` for the SNS/SQS adapter. See [asyncapi](#asyncapi) for what it writes of each Event, and [JSON Schema](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#json-schema) in SNAPSHOT.md for its schemas. An Application or a Definitions Package has none |
| `cf-loom verify` | Fails if `contract.snapshot.json`, the Handler map or the Readers file was edited or is out of date, if a Handler file the Handler map imports is missing or is no file, if a Handler the Handler map imported is left where the layout no longer places it, its declaration is Retired or gone, or its new path already holds a file, or if a generated file is left at a path the layout no longer names. It also fails on a Handler path that breaks the layout's rules once filled or that a link leads out of `src/` or into `src/contract/`, on a `handlerMap` or `readers` path that a link leads there, on a Handler that a file `generate` wrote imports at a path `generate` could not have placed, and on two declarations at one Handler path. It imports every `.ts` file under `src/contract/` but `*.test.ts` and `*.d.ts`, as `generate` does, and fails on the same exports and the same unlisted declarations; it writes nothing |
| `cf-loom package [--out <dir>]` | Writes the Contract Package of a Service or an Application to `<dir>`, `.cf-loom/contract-package/` next to package.json by default (it creates `.cf-loom/`, which holds only output, so keep it out of version control), a Service's, whose entry exports each Element under the name [The Root](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/contract/README.md#the-root) in the contract README gives (`getOrderEndpoint`, `orderCreatedEventV1`), ready for `tsc -p <dir>` (see [The Contract Package](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#the-contract-package) in the root ARCHITECTURE.md, which also says how `publish` generates it). It is generated from the committed `contract.snapshot.json`, which must be what `generate` would write, as `verify` compares it (see [Where it lives](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#where-it-lives) in SNAPSHOT.md); its `snapshot.json` is that file with the `generator` of the CLI that runs `package`. The folder must be missing, empty, or a previous output of any cf-loom, which holds only what `package` writes, beside a build's `dist/` or an install's `node_modules/`, which are kept while the rest is replaced: a `package.json` with `cfLoom`, `snapshot.json`, `tsconfig.json`, and regular files that start with the line `package` writes first (`// Generated by cf-loom package. Do not edit.`), wherever they sit in it; anything else, a symbolic link included, is refused and left as it was; these rules apply to that folder alone, never to the rest of `.cf-loom/`. A Definitions Package has no Contract Package: `publish` publishes it from its own package.json and built files |
| `cf-loom check [--json] [--prerelease] [--against <version\|dist-tag>]` | Runs the Compatibility Check of the committed `contract.snapshot.json`, which must be what `generate` would write, as for `package`, against the Baseline (see [The Baseline](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#the-baseline) in COMPATIBILITY.md; `--against` names another version it lists, or a dist-tag whose version it lists, instead), and prints every Change with its class and Verdict, every peer range that moved, and the version `publish` would take (see [Versioning](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#versioning) in COMPATIBILITY.md); it exits 2 when a Change needs a Breaking Change Approval, which your review process enforces (see [Breaking Change Approval](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#breaking-change-approval) in COMPATIBILITY.md). `--prerelease` derives the version as `publish --prerelease` does. With `--against` it derives no version, since that comparison is not the one `publish` makes, and with a Change refused it derives none either, since `publish` would refuse it |
| `cf-loom publish [--json] [--dry-run] [--force] [--prerelease]` | Runs the Compatibility Check of the committed `contract.snapshot.json`, which must be what `generate` would write, against the Baseline, and fails on a Change that is refused; it never waits on a Breaking Change Approval. It derives the version (see [Versioning](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#versioning) in COMPATIBILITY.md), merges the Baseline's history into the Snapshot, and publishes through your npm. A Contract Package is generated as `package` writes it, in `node_modules/<its name>` of a temporary folder under `node_modules/.cache/cf-loom` of the project; a Service's is built with the `typescript` installed there, whose `bin.tsc` `publish` runs (see [Set up](https://github.com/CasitaFeliz/cf-loom/blob/main/README.md#set-up) in the root README for its version), and an Application's, which has no code, is published as written. A Definitions Package must be built first: it is staged the same way, and before it is published `publish` imports it from there as a Service that installed it would, through its entry as Node resolves it (`exports`, else `main`), and exits 3 unless that import has the committed Snapshot; its files as `npm pack` lists them are published with `snapshot.json` (added to its `files` when the package lists any) and `cfLoom` (its `dependencies` empty) written in, its `version` set and its `peerDependencies` kept, with `zod` and `@cf-loom/contract` set to the ranges the CLI declares, as a Service's Contract Package's are, and compared with the Baseline's as [Versioning](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#versioning) says; a range in its `dependencies`, `optionalDependencies` or `peerDependencies` fails unless it is a version, a version range, a dist-tag, or an `npm:` alias of one whose name is a lower-case package name npm accepts (neither `node_modules` nor `favicon.ico`, as `package.json` must name the project), since npm publishes a range unchanged and no registry install resolves a `workspace:`, `catalog:`, `file:`, `link:` or `portal:` range, a path, a git URL, a GitHub shorthand or a tarball; this refuses some ranges npm would resolve, such as an alias of a name in upper case or one that ends `.tgz`, `.tar.gz` or `.tar`, and a range that ends so is refused too, while a malformed range or tag is kept (the two peers set to carets are read after they are set). `--prerelease` publishes `<version>-<n>` of the version it derives, which is how every package publishes before cf-loom 1.0.0 (see [Before cf-loom 1.0.0](#before-cf-loom-100)). `--dry-run` runs everything up to `npm publish`, the second read of the package's versions and `npm publish` itself excepted, builds and packs the package and reads its tarball as a publish would, removes the staging folder, and prints the version it would have taken. When nothing changed, `--force` publishes a patch, and `--prerelease` publishes nothing unless `--force` is given. Over a Baseline that is a prerelease, `publish` promotes it instead, with or without `--force`, by publishing its numbers as a version that is not a prerelease, and `--prerelease --force` publishes the next prerelease of those numbers. A version that would not be above the Baseline, as `--prerelease` derives over a Baseline named by hand such as `1.1.0-rc.1`, exits 3: publish a version above it by hand. It exits 3 when, right before `npm publish`, the package lists a version it did not list at the first read, and two publishes that derive the same version cannot both succeed: rerun the one that failed, which reads the registry again. |

Exit status: 0, done; 1, the check failed (a Change refused, or a Root, or a Snapshot, generated file or Handler file that `generate` must fix); 2, a Change needs a Breaking Change Approval; 3, a tooling error (configuration, registry, how the CLI was called). `--help`, `help` and `--version` exit 0. A command keeps what it found until it ends, and exits with the status that comes first among what it found and what stopped it: 3, then 1, then 2. stderr says each of them in that order, then the lines that carry no status, so a status-3 exit after the Compatibility Check still says that a Change is refused or needs an Approval. A command stops at its first failure, so `check` with a stale Snapshot ends with 1 before it reads the registry. `publish`, `broker-plan`, `openapi` and `asyncapi` never exit 2. `check` exits 3, as `publish` does, when the version it derives would not be above the Baseline.

### Before cf-loom 1.0.0

Until cf-loom 1.0.0 the Snapshot format is not frozen: format 1 still changes in place (see [Top level](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#top-level) in SNAPSHOT.md). So publish only prereleases, a Definitions Package included, with `check --prerelease` and `publish --prerelease`. A plain `publish` publishes a version that is not a prerelease: 1.0.0 for a package never published and, over a prerelease Baseline, its numbers promoted, even when nothing changed.

A Baseline that an older cf-loom published may be malformed for the one that runs. `check` and `publish` then exit 3 with `<spec>'s snapshot.json is malformed: <location> <reason>`, and the `generator` of that `snapshot.json` names the cf-loom that wrote it. Any older version an older cf-loom published may fail the same way, and `publish` always reads the Baseline, so the way out is a version above the Baseline that the running cf-loom reads, which you publish by hand once. Nothing judges what you publish by hand: no Change is compared and no Breaking Change Approval given. So publish it from the commit the Baseline was published from, after `cf-loom generate` with the running cf-loom, where the Contract is the Baseline's and nothing goes unchecked; `check --prerelease` and `publish --prerelease` then judge the Contract at HEAD against it, as for any Baseline.

For a Service or an Application, `cf-loom package` writes the package as `publish` would, with `version` 0.0.0 in package.json, none in `snapshot.json` and no history. In `.cf-loom/contract-package/`:

- In package.json, set `version` to a version above the Baseline's, a prerelease only when the Baseline is one, such as `1.0.0-1` over `1.0.0-0`, or `1.0.1` over `1.0.0` (see [The Baseline](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#the-baseline) in COMPATIBILITY.md).
- In `snapshot.json`, add the same `version`, on each Retired Element the Contract still declares its `retiredIn`, the one the Baseline holds for it, and for a Service `formerInputs`: the Baseline's, written as below, or `[]` when it holds none. A published Service Snapshot without that key is malformed.
- In `snapshot.json`, copy what only the Baseline knows (see [Where it lives](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#where-it-lives) in SNAPSHOT.md): the tombstones of deleted Retired Endpoints, Events and Commands, the removed codes, the removed Subscriptions and the Former Inputs. The Check then still refuses to reuse a Retired Element's identity or a removed Subscription's name, compares a removed code declared again with what it last had, and an Endpoint's query and body with each Former Input. `check` reads them only once the version is published, so write each in the current format: a removed code with the `headers` of a code (see [Rejection codes](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#rejection-codes) in SNAPSHOT.md), a tombstone as [Lifecycle and tombstones](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#lifecycle-and-tombstones) says, a removed Subscription as [Subscriptions and Dependencies](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#subscriptions-and-dependencies) says, a Former Input as [Former Inputs](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#former-inputs) says. A copied tombstone, code, Subscription or Former Input that is not makes that version malformed too, and the next one is then published by hand the same way.
- For a Service, build it with `npx tsc -p .cf-loom/contract-package`.
- Publish it with `npm publish .cf-loom/contract-package --tag latest`; npm refuses a prerelease without a tag.

A Definitions Package has no `cf-loom package`: publish it from its own package.json and built files, in a copy of the project, or restore the package.json afterwards. Set `version`; replace each `workspace:` or `catalog:` range; set `zod` and `@cf-loom/contract` in `peerDependencies` to the ranges [Versioning](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#versioning) in COMPATIBILITY.md gives; list `snapshot.json` in `files`; write `cfLoom` as `{ "format": 1, "snapshotHash": <the SHA-256 of contract.snapshot.json>, "kind": "definitions", "dependencies": {} }`, a hash no cf-loom command reads; and add `snapshot.json`, the committed `contract.snapshot.json` with that `version`, a `generator` and the history copied as above. Then `npm publish --tag latest`.

A Consumer whose `client()`, or whose `fakeProvider` of `@cf-loom/testing`, finds a Provider's exported Snapshot malformed after the same upgrade (see [Consuming a Contract](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/client/README.md#consuming-a-contract) in the client README) needs a version of that Provider's Contract Package published with the running cf-loom: the Provider publishes one, by hand as above if its Baseline is malformed, and the Consumer installs it, upgrading its @cf-loom packages where the peer range of that version asks for the cf-loom that published it.

Each command prints one line per thing it did or found, never a stack trace; `openapi` and `asyncapi` print their documents instead:

| Command | Prints |
| --- | --- |
| `init` | `Created <Root file>`, then `Created .gitattributes` when it wrote one, or `Updated .gitattributes` when it appended to one |
| `generate` | `Moved <old> to <new>` for each Handler it moved, in code point order of `<old>`, then `Wrote <path>` for each file it wrote, `contract.snapshot.json` first, then the Handler map, the Readers file and each new Stub, then `Deleted <path>` for each file it wrote that is left at a path the layout no longer names, in code point order |
| `verify` | `<path> is up to date` for each file it compared |
| `package` | `Wrote <dir>` |
| `check` | `Checked against <package>@<version>`, followed by `(no stable version cf-loom published: the first is <first>)` when the Baseline is a prerelease, `<first>` being 1.0.0, or the next major above the highest version the package lists that is not a prerelease, or, when higher, the numbers of the Baseline, or `(--against)` when `--against` named the version; then one line per Change; then one line per peer range that moved, by name in code point order, `Peer <name> moves from <range> to <range>: major` or `: minor`, `Peer <name> added <range>: minor` or `Peer <name> dropped <range>: minor` (a peer moving to a new major is packaging, not a Breaking Change, so it is no Change line); then, unless the version would not be above the Baseline, which ends the lines there, `No Change needs a Breaking Change Approval` when there is a Change and none is refused or needs one; then exactly one closing line, none with `--against` or a refused Change: `Would publish <package>@<version> (<why>)`, `<version>` being the version `publish` would take, or, with `--prerelease`, its prerelease `<version>-<n>`, and `<why>` being `major`, `minor` or `patch`, `first version` for a package with no Baseline, `promotes <baseline>` when the Baseline is a prerelease and nothing changed, or `above <version>, which cf-loom did not publish` when the version is the next major above a listed version that is not a prerelease and that cf-loom did not publish; or `Nothing to publish: the Snapshot and peer ranges are those of <package>@<version>` when no Change was found and no peer range moved. | `broker-plan` | `Stream <stream>: <subject> …`, each subject separated by a space, then `Durable consumer <durable> on <stream>: <subject>` for each Durable consumer, each in code point order, or `<service> needs no stream and no Durable consumer` |
| `openapi` | the OpenAPI document as JSON indented by two spaces (see [openapi](#openapi)) |
| `asyncapi` | the AsyncAPI document as JSON indented by two spaces (see [asyncapi](#asyncapi)) |
| `publish` | `Checked against <package>@<version>`, or `<package> has no Baseline: <reason>`, one line per Change and one line per peer range that moved, as `check` prints them, printed as soon as the version is derived, before the package is staged, built and put, so a run that fails or is killed meanwhile has said what the Check found; then `Published <package>@<version>`, or `Nothing to publish: the Snapshot and peer ranges are those of <package>@<version>; --force publishes anyway`, or with `--dry-run` `Would publish <package>@<version> (<why>): --dry-run stopped before npm publish`, `<why>` being what `check` prints, or `forced` when `--force` takes a version though nothing changed and no prerelease Baseline is promoted; and on stderr, with the exit status the publish had, `node_modules/.cache/cf-loom/publish-<id> was left behind: <reason>: delete it` when it could not remove the folder it staged the package in |

Every line on stdout or stderr, the `--json` document included, is written as cf-loom writes every line (see [Runtime](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#runtime) in the root ARCHITECTURE.md), so no reader splits a line there.

A Change is one line, `<site> <difference>[ <shape>][ at <path>][ (<position>)][ <field>=<value>…]: <class>[, <verdict>][; <hint>]`, in the order of the report: the kinds of the Difference and, for a schema, of its shape, from the tables below; its path, when it has one; its Position, when the path does not start with it; and every other field of the Difference and of its shape, in the order of the tables, as `name=value`. A `value` is written as JSON, so `1` and `"1"` differ. Any other path segment or text that is not made of ASCII letters, digits and `_ @ / $ -` is written as JSON too (`"two words"`, `"two\nlines"`), so a key with a space or a line break never splits the line. `<site>` is one of `endpoints.<identity> (<name>)`, `events.<Name@n>`, `commands.<Name@n>`, `codes.<CODE>`, `standardRejections.<name>`, `subscriptions.<name>`, `dependencies.<service>`, `exports.<name>`, `groups.<name>` or `guards.<name>`, a Service's Guards included; a failure names its site the same way, and adds `(root)` for the Root and `defs.<id>` for a recursive schema (see [Failures](#failures)). `<class>` is `Breaking`, `Additive` or `Neutral`, and the Verdict (see [Breaking Change Approval](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#breaking-change-approval) in COMPATIBILITY.md) adds to it `needs a Breaking Change Approval`, or `refused`; a Breaking Change that is allowed says `needs no Approval`, and an Additive or Neutral one that is allowed adds nothing:

```
endpoints.GET /orders/{} (getOrder) schema field-removed at success.body.total: Breaking, needs a Breaking Change Approval
endpoints.GET /orders/{} (fetchOrder) renamed from=getOrder to=fetchOrder baselineVisibility=public: Breaking, needs a Breaking Change Approval
events.OrderCreated@1 schema field-removed at body.total (message): Breaking, refused; make the change in a new Message Version
commands.ChargeCard@1 retired: Breaking, needs no Approval
```

The path is where the Difference is, in the author's terms: the part of the Endpoint it sits in (`input`, `success`; `params`, `query`, `headers`, `body`), a Rejection's `headers` or `body`, or a Guard's `demands`; then `.field` for an object's field, `[]` for an array's items, `[<i>]` for a tuple's item or an intersection's side, counted from zero, `{}` for a record's value, `{key}` for its key, `[...]` for a tuple's `rest`, `<|<i>>` for an option of a union, and `<discriminator=value>` for a variant of a discriminated union: `success.body.orders[].lines[].kind<type="a">.x`. A Difference inside a recursive schema, which the proposed Contract reaches through a `ref`, is at its path from that schema: `defs.<id>`, with the id the proposed Contract gives it, then the steps inside it (`defs.tree.children[].label (success)`), so it reads the same whichever path reaches the schema first; a recursive schema's own annotations are at `defs.<id>` alone, and a `ref`'s own def name and annotations stay where the `ref` sits. A Change at the root of an exported schema has no path. The Position, `input`, `success` or `message`, is written after the path when the path does not start with it (`at body.total (message)`, `at demands.query.token (input)`).

The hint says how to avoid a Change, from a closed table; the first row that fits decides:

| When | Hint |
| --- | --- |
| `deleted` | `retire it instead, deprecating it first if it is not, and delete it once the Baseline has it Retired` |
| `retired-before-deprecated` | `deprecate it in one publish and retire it in a later one` |
| `header-refuses-text` | `accept any text` |
| `name-kind-changed` | `declare it under a new name` |
| a Breaking `field-added` that is required | `make it optional` |
| a Breaking Change to an Event's or a Command's body, or `identity-reused` on one | `make the change in a new Message Version` |

### --json

With `--json`, a command prints one document on stdout, a single line, instead of its lines; stderr keeps its lines. The document starts with `format`, which is `2`, and `status`, the exit status. A command that wrote lines on stderr prints them (the Root's rules, a stale Snapshot, a tooling error, a usage error, `--json` written wrongly included, `check`'s refused Changes and needed Approvals, the version that would not be above the Baseline, or the versions the registry does not list that `check` reports with status 0) as `errors`, and a command that stopped after it did part of its work keeps that part beside them: the Handlers `generate` moved and the files it wrote and deleted, and the Changes of `check` and `publish`. `publish --json` prints none of the lines it prints while it runs, since its document holds the Changes. `published` is true only when `publish` saw `npm publish` succeed. A status-3 document may follow a put that reached the registry (npm printed no JSON, timed out or was stopped), so rerun `publish`, which reads the registry again.

```ts
type Failed = { format: 2; status: 1 | 3; errors: string[] };   // what stderr says when the command stopped before it did any of its work
type Bump = 'major' | 'minor' | 'patch';
type Peer = { name: string; from: string | null; to: string | null; bump: 'major' | 'minor' };
type Visibility = 'public' | 'internal' | 'private';

type CheckJson =
  | Failed
  | {
      format: 2;
      status: 0 | 1 | 2 | 3;              // 3 when the version publish would take would not be above the Baseline
      errors?: string[];                  // what stderr says: present when it has lines, as with status 1, 2 or 3
      package: string;
      baseline: string | null;            // the version compared with: the Baseline, or the one --against names
      stable: string | null;              // the highest version the package lists that is not a prerelease
      reason: string | null;              // why there is no Baseline, as the line says it
      changes: {                          // with no Baseline too: the Message Versions numbered after a gap
        site:                             // where the Change is, with the Visibility that decides its bump
          | { kind: 'endpoint'; identity: string; name: string; visibility: Visibility }
          | { kind: 'event' | 'command'; identity: string; visibility: Visibility }
          | { kind: 'code'; code: string; visibility: Visibility }
          | { kind: 'subscription' | 'dependency' | 'export' | 'guard' | 'group' | 'standard-rejection'; name: string; visibility: Visibility }
          | { kind: string; visibility: Visibility; /* … */ };   // a kind a later cf-loom adds (see the end of this section)
        difference: { kind: string; /* … */ }; // the Difference, with the fields the tables above list; a schema Difference's `shape` is the object { kind: string; /* … */ } of its shape's fields, and `at` is the Snapshot's own path, ["success", "body", "fields", "total"], or, inside a recursive schema, that of the proposed Snapshot's `defs`, ["defs", "tree", "fields", "label"]
        path: string | null;              // in the author's terms; none when the Difference has no `at`, or its `at` is the root of an exported schema
        class: 'breaking' | 'additive' | 'neutral';
        verdict: 'allowed' | 'approval-needed' | 'refused';
        hint: string | null;
      }[];
      peers: Peer[];                      // the peer ranges that moved, by name; [] with no Baseline, with --against, or with a Change refused
      bump: Bump | null;                  // the bump the Changes and the peers give; null when nothing moved, with no Baseline, with --against, or with a Change refused
      version: string | null;             // the version publish would take; null with --against, with a Change refused, when there is nothing to publish, or when it would not be above the Baseline
      tag: 'latest' | 'next' | null;      // its dist-tag; null exactly when version is
    };

type PublishJson =
  | Failed
  | (Exclude<CheckJson, Failed> & { status: 0 | 1 | 3 } & {
      published: boolean;                 // true when publish saw npm publish succeed; false with --dry-run, when there was nothing to publish, with a Change refused, and when it stopped first
    });

type BrokerPlanJson = Failed | { format: 2; status: 0; plan: BrokerPlan };      // the Broker plan the messaging README shows
type DocumentJson = Failed | { format: 2; status: 0; document: object };        // openapi and asyncapi
type InitJson = Failed | { format: 2; status: 0; created: string[]; updated: string[] };
type GenerateJson =
  | { format: 2; status: 0; moved: { from: string; to: string }[]; wrote: string[]; deleted: string[] }
  | (Failed & { moved?: { from: string; to: string }[]; wrote?: string[]; deleted?: string[] });   // each step it reached, with what it did before it stopped
type VerifyJson = Failed | { format: 2; status: 0; upToDate: string[] };
type PackageJson = Failed | { format: 2; status: 0; wrote: string };
type HelpJson = { format: 2; status: 0; usage: string };                         // --help, -h, help
type VersionJson = { format: 2; status: 0; name: string; version: string; snapshotFormat: number };   // --version
```

A key is the verb of the line it replaces: `Wrote x` is `wrote: [x]`. The path of a Change is the path as the line writes it, and `hint` the hint it ends with. A package that npm cannot find, or none of whose versions cf-loom published, has no Baseline, and `check` exits 0 without `--against` unless a version gap is refused. To fail a pipeline when nothing was compared, test `baseline`, keeping `check`'s own status, with a Breaking Change that waits for its Approval (exit 2) passing as in [Check in CI](https://github.com/CasitaFeliz/cf-loom/blob/main/README.md#check-in-ci) in the root README:

```bash
s=0; out=$(cf-loom check --json) || s=$?
[ "$s" -eq 0 ] || [ "$s" -eq 2 ] || exit "$s"
jq -e '.baseline != null' <<<"$out" >/dev/null
```

A pipe into `jq` would lose `check`'s status: under `pipefail` its exit 3 becomes `jq`'s 1, since that document has no `baseline`.

`format` is the version of these documents. A later cf-loom keeps `format` 2 while it only adds: a key, a kind of site, of Difference or of a shape, or a field of one. A reader ignores what it does not know, and judges a Change it cannot read by its `class` and `verdict`; the types above show these kinds as `kind: string`. Removing or renaming a key, giving a value another type or meaning, or adding a value to `status`, `class`, `verdict`, `bump`, `tag` or a Visibility is a new `format`.

### openapi

`cf-loom openapi` prints one OpenAPI 3.1.1 document for the Service as JSON indented by two spaces; a failure prints nothing on stdout (with `--json`, the errors document). `info` is the Service's name at version `0.0.0`, as `package` writes, and `tags` are the Groups that list an Endpoint, in code point order, each `{ "name", "description" }` with the Group's description. The document names no `servers`, which belong to your organization, and the only security schemes it names are those of the `authorization` header (see below). It describes what `serve` answers, so every Endpoint is written, whatever its Visibility, and your organization filters them (`jq` on `x-cf-loom-visibility`). A body is keyed by `application/json`.

A path is the Endpoint's, each param written in braces (`GET /orders/{}` with `["orderId"]` is `/orders/{orderId}`); the paths are in code point order, and the Endpoints of one path share a path item, each under its method in lower case. OpenAPI allows one template per path, so two Endpoints that name a param of one path differently fail (see the exit 3 lines above). An OpenAPI operation holds:

| Field | From the Endpoint |
| --- | --- |
| `operationId`, `tags`, `description` | its name, its Group in a list, its description |
| `deprecated: true` | a Deprecated or Retired Endpoint |
| `x-cf-loom-visibility`, `x-cf-loom-guards` | its Visibility, and its Guards as `[{ "guard": "apiKey", "qualifier": null }]`, as the Snapshot lists them |
| `parameters` | the path params in the path's order (`in: path`, required), then each query field, then each header field, Guards' demands included but the `authorization` header, names as the Snapshot stores them; `required` as declared, a list query param has an `array` schema, and the schema's `description` is also on the parameter. OpenAPI tools ignore a header parameter named `accept`, which is written all the same |
| `requestBody` | the Input body, required, as JSON; none when it has none |
| `responses` | by status, below |
| `security` | the `authorization` header's schemes, below; none without that header |

The responses are one per status, in status order; when several answer one status they are joined, their descriptions with `; ` and their schemas as `oneOf`. A Rejection answers as a body of `{ "$ref": "#/components/schemas/<CODE>" }`, described `<CODE>: <message>`:

| Status | Response |
| --- | --- |
| the Success's | `Success`, with its headers (each with its `description`) and its body; none for a body-less Success such as a 204 |
| each Rejection code's | the Endpoint's own, its Guards', invalid-input and not-implemented, and not-found when it lists it, with the headers the code declares (each with its `description`), required in the response only when every code of that status requires it, and, when the codes declare one name with different schemas, `oneOf` them with their descriptions joined |
| 500 and 503 | `FaultEnvelope`: a Fault that is not retryable (or `INVALID_OUTCOME`), and a retryable one, which may carry `retry-after` |
| 413 | `FaultEnvelope`, for `BODY_TOO_LARGE`, only for an Endpoint with an Input body, and when `serve` is given `maxBodyBytes` as a number |

A Deprecated Endpoint's every response carries the header `deprecation` with the `const` `@<unix seconds>` of its `deprecatedAt`. A Retired Endpoint that is still declared answers only `410` with `RETIRED`, before any Guard, so it keeps its path params and nothing else of its Input.

The `authorization` header is no header parameter, since OpenAPI tools ignore one: it is a security scheme. Each Guard of an Endpoint that is not Retired that demands an `authorization` header is the scheme `components.securitySchemes.<Guard name>`, `{ "type": "apiKey", "in": "header", "name": "authorization" }`; an `authorization` header that no Guard demands, so the Endpoint's own, is the scheme `authorization`. The OpenAPI operation's `security` is one requirement naming every such scheme in code point order, followed by `{}` as an alternative when the header is optional. A document with no such header has no `securitySchemes`.

A literal or closed enum of values of different JSON types, such as `z.literal(['a', 1])`, is written with a `type` list and its `enum`; as a query param or header, a validator that coerces text to the first type that fits may refuse text `serve` accepts (`"1"`).

`components.schemas`, in code point order, holds: `RejectionEnvelope` and `FaultEnvelope`, as [Over HTTP](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-http) in the root ARCHITECTURE.md describes them; one component per code an Endpoint that is not Retired answers, the `RejectionEnvelope` narrowed to its code as a `const`, any `message` text, and the body it declares (`false`, with no `body` key, when it declares none); and each recursive def a written schema reaches, as `<Id>Def` (see [JSON Schema](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#json-schema) in SNAPSHOT.md).

### asyncapi

`cf-loom asyncapi` prints one AsyncAPI 3.1.0 document for the Service as JSON indented by two spaces; a failure prints nothing on stdout (with `--json`, the errors document). `info` is the Service's name at version `0.0.0`, as `package` writes, with `tags`, the Groups of the Events it writes, each once, in code point order, each `{ "name", "description" }` with the Group's description, and `defaultContentType` is `application/json`, since every body is JSON. The document names no `servers`, which belong to your organization. It describes what the Service's EventPublisher publishes (see [Publishing and sending](https://github.com/CasitaFeliz/cf-loom/blob/main/packages/messaging/README.md#publishing-and-sending) in the messaging README), so every Event that is not Retired is written, whatever its Visibility, and your organization filters them (`jq` on `x-cf-loom-visibility`, below). Only Events are written: no Command, and no Subscription, since a Subscription to another Service's Event is described by its Provider's document.

Each Message Version is a channel keyed by its identity (`OrderCreated@2`), in code point order, with one AsyncAPI message and one AsyncAPI operation keyed by the same identity:

| Field | From the Message Version |
| --- | --- |
| `channels.<identity>.address` | its subject, `orders-service.event.OrderCreated.v2`, with the prefix in front when `--prefix` is given (see [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker) in the root ARCHITECTURE.md) |
| `channels.<identity>.x-cf-loom-visibility` | its Visibility, `internal` or `private` |
| `messages.<identity>.name`, `title` | the Event's name, and the identity |
| `messages.<identity>.description` | the Event's description |
| `messages.<identity>.headers` | `{ "$ref": "#/components/schemas/BrokerHeaders" }` |
| `messages.<identity>.payload` | the body as JSON Schema draft-07, which AsyncAPI's Schema Object extends (see [JSON Schema](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#json-schema) in SNAPSHOT.md); since AsyncAPI ignores what sits beside a `$ref`, a recursive def with a `description` or `examples` is `{ "allOf": [{ "$ref": … }], "description": … }`, and `deprecated: true` is added for a Deprecated Message Version, beside that `allOf` (which a body that is a bare `$ref` gets for the purpose) |
| `channels.<identity>.bindings` | with `--broker sqs` only, `{ "sns": { "name": "<topic>", "bindingVersion": "0.1.0" } }`: the SNS topic every Message of the Service is published to, its Stream's name with the prefix in front, as `broker-plan` prints it |
| `operations.<identity>` | `{ "action": "send", "channel": { "$ref": "#/channels/<identity>" }, "tags": [{ "name": "<its Group>" }], "messages": [{ "$ref": "#/channels/<identity>/messages/<identity>" }] }` |

A Retired Message Version is not published, so it has no channel and no AsyncAPI operation, and a recursive def only it reaches is no component. AsyncAPI has no `deprecated` on a channel, an AsyncAPI message or an AsyncAPI operation, which is why a Deprecated Message Version marks its `payload`.

`components.schemas`, in code point order, holds `BrokerHeaders`, when the document has a channel, and each recursive def a `payload` reaches, as `<Id>Def`. `BrokerHeaders` describes the headers every Message travels with on the Broker `--broker` names (see [Over the Broker](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#over-the-broker) in the root ARCHITECTURE.md). On JetStream, the default, `Cf-Loom-Fact-Id` and `Nats-Msg-Id` are required, non-empty strings, and any other header is a string; Transport headers are those outside the `Cf-Loom-` and `Nats-` namespaces. With `--broker sqs`, it describes the four String message attributes every Message travels with on SNS/SQS instead (see [On SNS/SQS](https://github.com/CasitaFeliz/cf-loom/blob/main/ARCHITECTURE.md#on-snssqs) in the root ARCHITECTURE.md): `cf-loom-subject`, the subject with the Broker prefix in front, as is, which is the channel's address and what each Durable consumer's SNS subscription filters on; `cf-loom-message-id` and `cf-loom-fact-id`, the Broker message id and the Fact id, each a JSON string with its quotes; and `cf-loom-headers`, the Transport headers as one JSON object, `{}` when there are none; the last three in ASCII JSON. All four are required, non-empty strings, and no other attribute is sent. The AsyncAPI operation has no binding in either case: SNS's operation binding names the topic's consumers, which a Provider's document does not know.

To keep the channels a Subscriber may read, drop the Private ones and their AsyncAPI operations:

```sh
cf-loom asyncapi | jq '[.channels | to_entries[] | select(.value["x-cf-loom-visibility"] == "private") | .key] as $private | del(.channels[$private[]], .operations[$private[]])'
```
