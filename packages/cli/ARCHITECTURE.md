# Internals of @cf-loom/cli

How the package's `src/` is split into modules, as [Package layout](../../ARCHITECTURE.md#package-layout) in the root ARCHITECTURE.md requires. `cf-loom check` and `cf-loom publish` (see [Commands](README.md#commands)) read the Baseline from the registry through the organization's npm as [The Baseline](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#the-baseline) in COMPATIBILITY.md and [Where it lives](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#where-it-lives) in SNAPSHOT.md say.

## Modules

The entry `src/index.ts` (`.`) re-exports from `config/`, and `src/internal/index.ts` (`./internal`) from `registry/`, the step `check` and `publish` share; `src/bin.ts` parses the arguments, runs a command and prints what it ends with, a throw (a bug of cf-loom) included, which ends as a tooling error.

| Module | Holds | Depends on |
| --- | --- | --- |
| `child-process/` | a program run with no shell and how it ended, a failure as a value of one line, and a text's first line or on one line | none |
| `loading/` | importing a user's TypeScript file in one line of failure, the project's package.json, where each kind of root sits, the root and its kind, the Definitions Packages a root lists as the root file resolves them, the version of an installed package, the files under a folder through linked folders, where each declaration is exported, and the npm name a project publishes as | `child-process` |
| `config/` | `defineConfig`, `Config`, `Layout`, the layout's rules and defaults, and loading `cf-loom.config.ts` | `loading` |
| `project/` | a project as every command but `init` reads it: its package, configuration and root, the committed `contract.snapshot.json` as read, and the valid root with its canonical Snapshot; a failure is a closed value, the root's rules broken or a tooling error | `config`, `loading` |
| `source-text/` | spelling generated TypeScript: the header line, string and JSON literals, identifiers, import lines and relative `.ts` specifiers, a module from its imports and body | none |
| `schema-code/` | a Snapshot node as a zod expression, `declared` or `reader`, the Unknown cases of readers, what generated code imports, the recursive defs with their types, and the line saying which recursion ids cannot be named in code | `source-text` |
| `json-schema/` | a Snapshot node as JSON Schema 2020-12 or draft-07, and the components of the recursive defs some nodes reach, named as their types in code | `schema-code` |
| `openapi/` | the OpenAPI document of a Service's Endpoints from its Snapshot: paths, operations, parameters, request bodies, responses by status, the `authorization` header written as security schemes, the Envelopes and the codes as components | `json-schema` |
| `asyncapi/` | the AsyncAPI document of a Service's Events from its Snapshot: a channel, a message and a send operation per Message Version that is not Retired, the broker headers and the recursive defs as components | `json-schema` |
| `service-code/` | what `generate` writes into a Service: the Handler map with the Deprecated Endpoints' stamps, the Reader schemas of its own Events and Commands, and each Command's Message Version and Subscription paired with its Reader, reached through the root, each stub, the Handler path of each Element from the layout, with its name in kebab-case, and the Elements at one path, whether a file starts with the line `generate` writes first, and the names in code it writes with the Subscription that would take another's | `config`, `source-text`, `schema-code`, `loading` |
| `contract-package/` | the Contract Package's files from a canonical Snapshot and its text: package.json with `cfLoom` and the hash, `snapshot.json`, tsconfig, the entry with the types of the defs it reaches, the exported Snapshot as `@cf-loom/contract` cuts it, as a module, the Standard Rejections, and the code of what the cut holds (one file per exported Endpoint, per exported Event's Message Version, per Guard they reach and per code they answer, and the recursive defs they reach); an Application's Snapshot alone; the paths a package holds; and the codes or recursion ids that cannot be named in code; from a declared or a published Snapshot; a Definitions Package's own package.json as published | `source-text`, `schema-code`, `loading` |
| `registry/` | reading a package's Baseline through the organization's `npm` (run with no shell in the project's directory and environment): the versions, the highest that is not a prerelease, its `cfLoom`, peer ranges and sha512 digests, its packed tarball hashed against them and read by hand for the one `snapshot.json` npm unpacks, from an archive of only what `npm pack` writes, and `pnpm pack` for paths that fit a ustar header, for printable-ASCII paths without `:` or `\` (version 00 headers of files and empty folders, and before an entry one pax header of ASCII bytes holding only its path, modification time and size, each record led by a length without a leading zero; any other tar entry, and any other path, is refused), and decoded with `@cf-loom/contract/internal`, and, for a package npm cannot find, the user npm logs in as on the scope's registry; a failure is a value of one line, without the credentials of any URL in it; publishing a staged folder with `npm publish --tag <tag> --ignore-scripts`, and listing a package's own files with `npm pack --dry-run` | `child-process`, `loading` |
| `writing/` | writing generated files atomically, a stub only where none is, and the Contract Package over a missing, empty or previous output, its install and build kept; temporary staging folders | `contract-package`, `loading` |
| `building/` | building a staged package with `tsc -p`, the TypeScript installed where the root imports packages | `child-process`, `loading` |
| `commands/` | `init`, `generate`, `verify`, `package`, `check`, `broker-plan`, `openapi`, `asyncapi` and `publish`, each ending with its exit status and the lines it prints, and their steps: the stubs, the Handler files, the orphan files, the regenerated files, a Change on one line, the broker plan's lines, and the version `publish` derives | `config`, `child-process`, `loading`, `project`, `registry`, `service-code`, `contract-package`, `openapi`, `asyncapi`, `writing`, `building` |

Every Endpoint, Guard, Rejection, def and Event a Contract Package's code declares has a name in code that says its kind, so names of different kinds never meet: `<name>Endpoint`, `<name>Guard`, `<code in camelCase>Rejection`, `<id in camelCase>Def` and `<id in camelCase>ReaderDef` with their types in PascalCase, and `<name with its first letter lower-cased>EventV<n>` for an Event's Message Version (`paymentSettledEventV1`); `@cf-loom/contract` is imported whole as `loom` and `zod` as `z`. A recursive def is a `z.lazy` annotated with its written type, `z.ZodType<TreeDef, TreeDef>` as declared, input and output exact, and `z.ZodType<TreeReaderDef>` as a reader; an object def is also `z.core.$ZodTypeDiscriminable`, so zod's discriminated union takes it as a variant with no cast, and a written type that disagrees with the schema fails `tsc`. What `generate` writes into a Service is named so: in the readers file, `<name in code>Reader` for an own Message Version's Reader schema, and each pairing under its name in code, `chargeCardV1` for a Command's Message Version and its name, `notifyOnSettled`, for a Subscription; in the Handler map, the locals `<name>EndpointHandler`, `<name>GuardHandler`, `<name in code>CommandHandler` and `<name>SubscriptionHandler`; a Subscription's pairing is the one name with no fixed ending, so it alone can meet another name of the file (see [What the commands print and write](README.md#what-the-commands-print-and-write) in the README).

A command takes where and when it runs (the working directory, the environment npm runs with, and the clock) from `bin.ts`. Every command but `init` first builds the project through `project/`: its valid root and the declared Snapshot, with `@cf-loom/contract/internal`; then `generate` and `verify` write or compare the generated files, and `package`, once the committed Snapshot is that Snapshot, writes the Contract Package from it. `check`, once the committed Snapshot is that Snapshot, reads its Baseline and runs the Compatibility Check. `broker-plan`, once the committed Snapshot is that Snapshot, derives the broker plan with `@cf-loom/contract/internal` and prints it. `openapi`, once the committed Snapshot is that Snapshot, writes the OpenAPI document and prints it. `asyncapi`, once the committed Snapshot is that Snapshot, writes the AsyncAPI document and prints it. `publish`, once the committed Snapshot is that Snapshot, reads its Baseline, derives the version, stages and builds the package, and publishes it through npm.
