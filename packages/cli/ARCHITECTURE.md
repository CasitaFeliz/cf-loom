# Internals of @cf-loom/cli

How the package's `src/` is split into modules, as [Package layout](../../ARCHITECTURE.md#package-layout) in the root ARCHITECTURE.md requires. `cf-loom check` and `cf-loom publish` (see [Commands](README.md#commands)) read the Baseline from the registry through the organization's npm as [The Baseline](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#the-baseline) in COMPATIBILITY.md and [Where it lives](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#where-it-lives) in SNAPSHOT.md say.

## Modules

The entry `src/index.ts` (`.`) re-exports from `config/`, and `src/internal/index.ts` (`./internal`) from `registry/` and `versioning/`, reading the Baseline, which `check` and `publish` share, and deriving the version `publish` takes and `check` previews; `src/bin.ts` parses the arguments, runs a command and prints what it ends with, as its lines or, under `--json`, as the one document it holds or the errors document of its stderr lines, a throw (a bug of cf-loom) and a usage error included, which end as a tooling error, and ends the process with its status once the output is written, whatever a user's module keeps alive and whether or not a reader closed a stream.

| Module | Holds | Depends on |
| --- | --- | --- |
| `child-process/` | a program run with no shell and how it ended, a failure as a value of one line, and a text's first line or on one line | none |
| `versioning/` | which listed version is the highest, prereleases included, and which is the highest that is not a prerelease; how semantic versions order, whether one is a prerelease, the version a bump moves one to and the next prerelease of one's numbers; the version `publish` derives and `check` previews (the highest version that is not a prerelease bumped, or 1.0.0, never below a prerelease Baseline's numbers, which `publish` promotes when nothing changed), the dist-tag it takes, and a version that would not be above the Baseline, which `publish` and `check` refuse | none |
| `loading/` | importing a user's TypeScript file in one line of failure, the project's package.json, where each kind of root sits, the root and its kind, with what the root file exports by name, the packages the root's import reaches, as Node resolves them, the Definitions Packages among them, and the ones a root names, a staged package's root as a Service that installed it imports it, the version of an installed package, the files under a folder through linked folders, a path's identity as a file, links followed as far as it exists, what each file of the Contract exports, the npm name a project publishes as, and what a Snapshot file in a newer format says | `child-process` |
| `config/` | `defineConfig`, `Config`, `Layout`, the layout's rules and defaults, and loading `cf-loom.config.ts` | `loading` |
| `project/` | a project as every command but `init` reads it: its package, configuration and root, the committed `contract.snapshot.json` as read and whether it differs from the canonical Snapshot only by CRLF line endings, the valid root with its canonical Snapshot, the declared root of any loaded root (a staged package's too), and the CLI running; a failure is a closed value, the root's rules broken or a tooling error | `config`, `loading`, `writing` |
| `source-text/` | spelling generated TypeScript: the header line, string and JSON literals, identifiers, import lines and relative `.ts` specifiers, a module from its imports and body, and reading back a module's default imports and the path a specifier names | none |
| `schema-code/` | a Snapshot node as a zod expression, `declared` or `reader`, the Unknown cases of readers, what generated code imports, and the recursive defs with their types | `source-text` |
| `json-schema/` | a Snapshot node as JSON Schema 2020-12 or draft-07, and the components of the recursive defs some nodes reach, named as their types in code | `schema-code` |
| `openapi/` | the OpenAPI document of a Service's Endpoints from its Snapshot: paths, operations, parameters, request bodies, responses by status, the `authorization` header written as security schemes, the Envelopes and the codes as components | `json-schema` |

| `service-code/` | what `generate` writes into a Service: the Handler map with the Deprecated Endpoints' stamps, the Reader schemas of its own Events and Commands, and a `readers` table pairing each Command's Message Version and Subscription, imported from the file that exports it, with its Reader, each stub, the Handler path of each Element from the layout, with its Group and its name in kebab-case, and the line that stops placing them (a path under `src/contract/`, two Elements at one path), whether a file starts with the line `generate` writes first, and the Handlers a Handler map imports, read back from its text | `config`, `source-text`, `schema-code`, `loading` |

| `registry/` | reading a package's Baseline through the organization's `npm` (run with no shell in the project's directory and environment): the versions, the Baseline among them (the highest, prereleases included) or the version `check --against` compares with instead (itself or a dist-tag's), its `cfLoom`, peer ranges and sha512 digests, its packed tarball hashed against them and read by hand for the one `snapshot.json` npm unpacks, from an archive of only what `npm pack` writes, and `pnpm pack` for paths that fit a ustar header, for printable-ASCII paths without `:` or `\` (version 00 headers of files and empty folders, and before an entry one pax header of ASCII bytes holding only its path, modification time and size, each record led by a length without a leading zero; any other tar entry, and any other path, is refused), and decoded with `@cf-loom/contract/internal`, and, for a package npm cannot find, the user npm logs in as on the registry that serves the package's scope, or `registry=` for an unscoped one; a failure is a value of one line, without the credentials of any URL in it; publishing a staged folder with `npm publish --tag <tag> --ignore-scripts` after reading the versions again, to stop when a higher one was published meanwhile, and listing a package's own files with `npm pack --dry-run` | `child-process`, `loading`, `versioning` |

| `building/` | building a staged package with `tsc -p`, the TypeScript installed where the root imports packages | `child-process`, `loading` |

Every Endpoint, Guard, Rejection, def and Event a Contract Package's code declares has a name in code that says its kind, so names of different kinds never meet: `<name>Endpoint`, `<name>Guard`, `<code in camelCase>Rejection` (a word that starts with a digit keeps its underscore: `ORDER_V_2` is `orderV_2Rejection`), `<id>Def` and `<id>DefReader` with their types in PascalCase, and `<name with its first letter lower-cased>EventV<n>` for an Event's Message Version (`paymentSettledEventV1`); `@cf-loom/contract` is imported whole as `loom` and `zod` as `z`. A recursive def is a `z.lazy` annotated with its written type, `z.ZodType<TreeDef, TreeDef>` as declared, input and output exact, and `z.ZodType<TreeDefReader>` as a reader; an object def is also `z.core.$ZodTypeDiscriminable`, so zod's discriminated union takes it as a variant with no cast, and a written type that disagrees with the schema fails `tsc`. What `generate` writes into a Service is named so: in the readers file, `<name in code>Reader` for an own Message Version's Reader schema, which ends in `V<n>Reader`, `<id>DefReader` for a reader def, `<name in code>Command` and `<name>Subscription` for a Command's Message Version and a Subscription as it is imported, and the `readers` table, which holds each pairing under its name in code, `chargeCardV1` for a Command's Message Version and `notifyOnSettled` for a Subscription; in the Handler map, the locals `<name>EndpointHandler`, `<name>GuardHandler`, `<name in code>CommandHandler` and `<name>SubscriptionHandler`; no Subscription's name can meet another name of the file.

A command takes where and when it runs (the working directory, the environment npm runs with, and the clock) from `bin.ts`. Every command but `init` first builds the project through `project/`: its valid root and the declared Snapshot, with `@cf-loom/contract/internal`; then `generate` and `verify` write or compare the generated files, and `package`, once the committed Snapshot is that Snapshot, writes the Contract Package from it. `check`, once the committed Snapshot is that Snapshot, reads its Baseline, runs the Compatibility Check and derives the version `publish` would take from its Changes and the peer ranges the package would be published with. `broker-plan`, once the committed Snapshot is that Snapshot, derives the broker plan with `@cf-loom/contract/internal` and prints it. `openapi`, once the committed Snapshot is that Snapshot, writes the OpenAPI document and prints it. `asyncapi`, once the committed Snapshot is that Snapshot, writes the AsyncAPI document and prints it. `publish`, once the committed Snapshot is that Snapshot, reads its Baseline, derives the version as `check` does, stages the package, builds a Contract Package or imports a Definitions Package's built entry as an installed one and compares its declared Snapshot with the committed one, and, unless it is a dry run, reads the package's versions again and publishes it through npm.
