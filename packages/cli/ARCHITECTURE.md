# Internals of @cf-loom/cli

How the package's `src/` is split into modules, as [Package layout](../../ARCHITECTURE.md#package-layout) in the root ARCHITECTURE.md requires. `cf-loom check` and `cf-loom publish` (see [Commands](README.md#commands)) read the Baseline from the registry through the organization's npm as [The Baseline](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#the-baseline) in COMPATIBILITY.md and [Where it lives](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#where-it-lives) in SNAPSHOT.md say.

## Modules

The entry `src/index.ts` (`.`) re-exports from `config/`, and `src/internal/index.ts` (`./internal`) from `registry/` and `versioning/`, reading the Baseline, which `check` and `publish` share, and deriving the version `publish` takes and `check` previews; `src/bin.ts` parses the arguments, runs a command, prints each line the command finds as it comes, and prints what it ends with, as its lines or, under `--json`, as the one document it holds, with the fields the command found merged into it (a throw, a bug of cf-loom, included) and its stderr lines as `errors` when its status is not 0, or the errors document of a command that holds none, a usage error included, which ends as a tooling error as a throw does; it ranks the exit statuses as the CLI README says, and ends the process with its status once the output is written, whatever a user's module keeps alive and whether or not a reader closed a stream.

Every Endpoint, Guard, Rejection, def and Event a Contract Package's code declares has a name in code that says its kind, so names of different kinds never meet: `<name>Endpoint`, `<name>Guard`, `<code in camelCase>Rejection` (a word that starts with a digit keeps its underscore: `ORDER_V_2` is `orderV_2Rejection`), `<id>Def` and `<id>DefReader` with their types in PascalCase, and `<name with its first letter lower-cased>EventV<n>` for an Event's Message Version (`paymentSettledEventV1`); `@cf-loom/contract` is imported whole as `loom` and `zod` as `z`. A recursive def is a `z.lazy` annotated with its written type, `z.ZodType<TreeDef, TreeDef>` as declared, input and output exact, and `z.ZodType<TreeDefReader>` as a reader; an object def is also `z.core.$ZodTypeDiscriminable`, so zod's discriminated union takes it as a variant with no cast, and a written type that disagrees with the schema fails `tsc`. What `generate` writes into a Service names a Message Version as [The Root](../contract/README.md#the-root) in the contract README says, `<message>` being its name with the first letter lower-cased: in the readers file, `<message>ReaderV<n>` for an own Message Version's Reader schema, `<id>DefReader` for a reader def, `<message>CommandV<n>` and `<name>Subscription` for a Command's Message Version and a Subscription as it is imported, and the `readers` table, which holds each pairing under its key, `chargeCardV1` for a Command's Message Version and `notifyOnSettled` for a Subscription; in the Handler map, the locals `<name>EndpointHandler`, `<name>GuardHandler`, `<message>CommandHandlerV<n>` and `<name>SubscriptionHandler`; no Subscription's name can meet another name of the file.

A command takes where and when it runs (the working directory and the environment npm runs with), and the Run it reports what it finds through, from `bin.ts`. Every command but `init` first builds the project through `project/`: its valid Root and the declared Snapshot, with `@cf-loom/contract/internal`; then `generate` and `verify` write or compare the generated files, and `package`, once the committed Snapshot is that Snapshot, writes the Contract Package from it. `check`, once the committed Snapshot is that Snapshot, reads its Baseline, runs the Compatibility Check, derives the version `publish` would take from its Changes and the peer ranges the package would be published with, and reads which versions the Contract is declared against, its Providers' and its origins', the registry does not list. `broker-plan`, once the committed Snapshot is that Snapshot, derives the broker plan with `@cf-loom/contract/internal` and prints it. `openapi`, once the committed Snapshot is that Snapshot, writes the OpenAPI document and prints it. `asyncapi`, once the committed Snapshot is that Snapshot, writes the AsyncAPI document and prints it. `publish`, once the committed Snapshot is that Snapshot, reads its Baseline, derives the version as `check` does, stops on a version the registry does not list that the Contract is declared against, stages the package, builds a Service's Contract Package or imports a Definitions Package's built entry as an installed one and compares its declared Snapshot with the committed one, and, unless it is a dry run, reads the package's versions again and publishes it through npm.
