# Internals of @cf-loom/cli

How the package's `src/` is split into modules, as [Package layout](../../ARCHITECTURE.md#package-layout) in the root ARCHITECTURE.md requires. `cf-loom check` and `cf-loom publish` (see [Commands](README.md#commands)) read the Baseline from the registry through the organization's npm as [The Baseline](https://github.com/CasitaFeliz/cf-loom/blob/main/COMPATIBILITY.md#the-baseline) in COMPATIBILITY.md and [Where it lives](https://github.com/CasitaFeliz/cf-loom/blob/main/SNAPSHOT.md#where-it-lives) in SNAPSHOT.md say.

## Modules

The entry `src/index.ts` (`.`) re-exports from `config/`, and `src/internal/index.ts` (`./internal`) from `registry/`, the step `check`, `publish`, `broker-plan` and `route-plan` share; `src/bin.ts` parses the arguments, runs a command and prints what it ends with.

| Module | Holds | Depends on |
| --- | --- | --- |
| `loading/` | importing a user's TypeScript file in one line of failure, the project's package.json, where each kind of root sits, the root, the Definitions Packages a root lists as the root file resolves them, the version of an installed package, the files under a folder through linked folders, and where each declaration is exported | `contract-package` |
| `config/` | `defineConfig`, `Config`, `ApprovalSource`, and loading `cf-loom.config.ts` | `loading` |
| `project/` | a project as every command but `init` reads it: its package, configuration and root, the committed `contract.snapshot.json` as read, and the valid root with its canonical Snapshot; a failure is a closed value, the root's rules broken or a tooling error | `config`, `loading` |
| `source-text/` | spelling generated TypeScript: the header line, string and JSON literals, identifiers, import lines and relative `.ts` specifiers, a module from its imports and body | none |
| `schema-code/` | a Snapshot node as a zod expression, `declared` or `reader`, the Unknown cases of readers, what generated code imports, the recursive defs with their types, and the line saying which recursion ids cannot be named in code | `source-text` |
| `service-code/` | what `generate` writes into a Service: the Handler map with the Deprecated Endpoints' stamps, the Reader schemas of its own Events and Commands, and each Command's Message Version and Subscription paired with its Reader, reached through the root, each stub, the Handler paths its declarations name, and the names in code it writes with the Subscription that would take another's | `source-text`, `schema-code`, `loading` |
| `contract-package/` | the Contract Package's files from a canonical Snapshot and its text: package.json with `cfLoom` and the hash, `snapshot.json`, tsconfig, the entry with the types of the defs it reaches, the exported Snapshot as `@cf-loom/contract` cuts it, as a module, the Standard Rejections, and the code of what the cut holds (one file per exported Endpoint, per exported Event's Message Version, per Guard they reach and per code they answer, and the recursive defs they reach); an Application's Snapshot alone; the paths a package holds; the codes or recursion ids that cannot be named in code; and the npm name a project publishes as | `source-text`, `schema-code` |
| `registry/` | reading a package's Baseline through the organization's `npm` (run with no shell in the project's directory and environment): the versions, the highest that is not a prerelease, its `cfLoom`, peer ranges and sha512 digests, its packed tarball hashed against them and unpacked by hand to `snapshot.json`, as npm unpacks it, and decoded with `@cf-loom/contract/internal`, and, for a package npm cannot find, the user npm logs in as on the scope's registry; a failure is a value of one line, without the credentials of any URL in it | `contract-package`, `loading` |
| `writing/` | writing generated files atomically, a stub only where none is, and the Contract Package over a missing, empty or previous output, its install and build kept | `contract-package`, `loading` |
| `commands/` | `init`, `generate`, `verify` and `package`, each ending with its exit status and the lines it prints, and their steps: the stubs, the Handler files, the regenerated files | `config`, `loading`, `project`, `service-code`, `contract-package`, `writing` |

Every Endpoint, Guard, Rejection, def and Event a Contract Package's code declares has a name in code that says its kind, so names of different kinds never meet: `<name>Endpoint`, `<name>Guard`, `<code in camelCase>Rejection`, `<id in camelCase>Def` and `<id in camelCase>ReaderDef` with their types in PascalCase, and `<name with its first letter lower-cased>EventV<n>` for an Event's Message Version (`paymentSettledEventV1`); `@cf-loom/contract` is imported whole as `loom` and `zod` as `z`. A recursive def is a `z.lazy` annotated with its written type, `z.ZodType<TreeDef, TreeDef>` as declared, input and output exact, and `z.ZodType<TreeReaderDef>` as a reader; an object def is also `z.core.$ZodTypeDiscriminable`, so zod's discriminated union takes it as a variant with no cast, and a written type that disagrees with the schema fails `tsc`. What `generate` writes into a Service is named so: in `readers.generated.ts`, `<name in code>Reader` for an own Message Version's Reader schema, and each pairing under its name in code, `chargeCardV1` for a Command's Message Version and the camelCase of its name, `notifyOnSettled`, for a Subscription; in the Handler map, the locals `<name>EndpointHandler`, `<name>GuardHandler`, `<name in code>CommandHandler` and `<name in camelCase>SubscriptionHandler`; a Subscription's pairing is the one name with no fixed ending, so it alone can meet another name of the file (see [What the commands print and write](README.md#what-the-commands-print-and-write) in the README).

A command takes where and when it runs (the working directory and the clock) from `bin.ts`. Every command but `init` first builds the project through `project/`: its valid root and the declared Snapshot, with `@cf-loom/contract/internal`; then `generate` and `verify` write or compare the generated files, and `package`, once the committed Snapshot is that Snapshot, writes the Contract Package from it.
